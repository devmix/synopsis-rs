# knowledge-graph Specification

## Purpose

Локальный knowledge graph: производный in-memory индекс над SQLite (источник истины), BFS-траверсал с доменными границами, поиск сущностей, CEL-линковка выражениями и кросс-доменный пайплайн — фундамент MCP-инструментов графа.

## Requirements

### Requirement: Построение и загрузка индекса

Крейт `graph` строит производный индекс из SQLite при старте (флаг `load_on_startup`): узлы — сущности (`entities`), рёбра — связи (`entity_links`) + fact-рёбра; поддерживаются индексы name→ID («domain:lowercase_name», O(1)) и type→nodes. Пересоздание индекса — полный rebuild; инкрементальность не требуется. Источник истины — SQLite; сам индекс не персистентен.

#### Scenario: Загрузка при старте
- **WHEN** сервер стартует с `load_on_startup=true` и непустой БД
- **THEN** индекс построен из таблиц entities/entity_links; счётчики узлов/рёбер соответствуют содержимому БД

#### Scenario: Граф отключён
- **WHEN** `enable_graph=false` или `load_on_startup=false`
- **THEN** индекс не строится; запросы графа возвращают явное состояние «граф недоступен» (не ошибку)

#### Scenario: Пустая БД
- **WHEN** индекс строится на БД без сущностей
- **THEN** строится пустой валидный индекс; запросы возвращают пустые результаты

### Requirement: BFS-траверсал

Траверсал от сущности реализует следующий контракт: max_depth (default 5, максимум 10), max_nodes (default 1000; рёбра включаются только между вошедшими узлами), направление outgoing/incoming/both. Доменные границы строгие: fact-рёбра никогда не пересекают домены; пересечение возможно ТОЛЬКО через entity links и только при `FollowEntityLinks=true`.

#### Scenario: Траверсал в глубину
- **WHEN** выполняется траверсал с max_depth=N
- **THEN** возвращаются узлы по уровням BFS до глубины N; результат детерминирован

#### Scenario: Ограничение числа узлов
- **WHEN** траверсал достигает max_nodes
- **THEN** обход останавливается; len(edges) ≤ len(nodes)

#### Scenario: Доменная граница для fact-рёбер
- **WHEN** BFS встречает fact-ребро, ведущее в другой домен
- **THEN** переход блокируется независимо от флагов

#### Scenario: Переход через entity links
- **WHEN** `FollowEntityLinks=true` и встречено entity-link ребро в другой домен
- **THEN** переход разрешён; при `FollowEntityLinks=false` — заблокирован

### Requirement: Поиск сущностей

Индекс обеспечивает поиск: точный по (домен, имя) — O(1) через name→ID, регистронезависимо; частичный — prefix + substring в пределах домена, результат сортирован.

#### Scenario: Точный поиск
- **WHEN** ищется сущность по домену и имени
- **THEN** возвращается ID за константное время; регистр имени не важен

#### Scenario: Частичный поиск
- **WHEN** ищется по префиксу/подстроке
- **THEN** возвращается отсортированный список совпавших сущностей домена

### Requirement: Метрики и DOT-export

Индекс предоставляет статистику (число узлов, число рёбер, средняя степень) и экспорт в DOT-формат, валидный для graphviz.

#### Scenario: Статистика
- **WHEN** запрашивается статистика построенного индекса
- **THEN** node_count/edge_count/avg_degree соответствуют содержимому

#### Scenario: DOT-export
- **WHEN** индекс экспортируется в DOT
- **THEN** вывод парсится graphviz; узлы атрибутированы доменом/типом

### Requirement: CEL-линковка выражениями

Крейт оценивает CEL-выражения линковки из ontology.xml через крейт `cel` (замена cel-interpreter, решение человека 2026-08-22). Контекст выражения предоставляет функции контракта: `facts(entity)`, `has_fact(entity, key, value)`, `chunks(entity)`, `chunk_contains(entity, text)`, `neighbors(entity)`, `path_exists(from, to, max_depth)`; тяжёлые индексы (FactIndex/ChunkIndex/GraphIndex) грузятся лениво (scope cache). Результат оценки — решение «линковать ли пару сущностей».

#### Scenario: Оценка правила
- **WHEN** правило онтологии содержит выражение с has_fact/facts
- **THEN** функция возвращает данные фактов сущности из SQLite; выражение вычисляется без паники

#### Scenario: Графовые функции
- **WHEN** выражение использует neighbors/path_exists
- **THEN** функции читают in-memory индекс; path_exists ограничен max_depth

#### Scenario: Ленивые индексы
- **WHEN** выражение не использует chunks()
- **THEN** ChunkIndex не загружается (scope cache)

### Requirement: Кросс-доменный пайплайн линковки

Пайплайн применяет методы по порядку конфигурации: `equals` (точное совпадение имён), `expression` (CEL-правила), `llm` (LLM-сравнение пары через OpenAI-совместимый клиент). Каждый метод идемпотентен: повторная линковка не создаёт дубликатов (ON CONFLICT DO NOTHING через EntityLinkDao). Флаг `linker.disabled` отключает LLM-метод. LLM-метод для каждой пары: загружает контекст чанков обеих сущностей (до 3 текстов на сущность), рендерит шаблоны system/user (загрузка из `prompts_path`, embedded-fallback), вызывает LLM-клиент со структурированным выводом, парсит решение `{same_entity, confidence, reasoning}`, создаёт link только при confidence ≥ `llm_confidence_threshold` (method='llm', evidence=reasoning, confidence клампится в [0,1]); решение кэшируется в app_kv по хэшу (пара сущностей + хэши шаблонов) — повторный вызов той же пары не обращается к LLM. Сбой вызова/парсинга одной пары не прерывает пайплайн (фиксируется в результатах).

#### Scenario: equals-линковка
- **WHEN** две сущности разных доменов имеют одинаковые нормализованные имена
- **THEN** создаётся cross-domain link; повторный прогон не дублирует

#### Scenario: expression-линковка
- **WHEN** CEL-правило онтологии истинно для пары сущностей
- **THEN** создаётся link с типом/приоритетом правила

#### Scenario: LLM-линковка выше порога
- **WHEN** LLM валидно отвечает same_entity=true и confidence ≥ порога
- **THEN** создаётся link method='llm' с evidence=reasoning; решение записано в кэш

#### Scenario: LLM ниже порога
- **WHEN** confidence решения ниже `llm_confidence_threshold`
- **THEN** link не создаётся; решение кэшируется

#### Scenario: Кэш решений
- **WHEN** пара уже имеет кэшированное решение (те же хэши шаблонов)
- **THEN** LLM не вызывается; используется кэшированное решение

#### Scenario: Отказ одной пары
- **WHEN** вызов LLM или парсинг ответа для пары завершается ошибкой
- **THEN** ошибка фиксируется в результатах; пайплайн продолжает остальные пары

#### Scenario: LLM-стаб
- **WHEN** пайплайн доходит до метода llm
- **THEN** выполняется реальная LLM-линковка пары (стаб из change graph заменён: контекст → шаблоны → вызов клиента → решение); существующие линки не затрагиваются

#### Scenario: Отключение линкера
- **WHEN** `linker.disabled=true`
- **THEN** llm-метод исключён из пайплайна; equals/expression работают
