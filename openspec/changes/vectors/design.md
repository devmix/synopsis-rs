# vectors — Design

Реализация ADR 0003 (GO: LanceDB IvfHnswSq u8-SQ) в боевом крейте + каскадная согласованность с SQLite (решение человека 2026-08-21). Оракул (`../synopsis`) — референс по поведению, не по коду: vec0-таблицы жили внутри того же SQLite-файла, поэтому в Go синхронность достигалась одной транзакцией (`internal/gc/documents_gc.go`: `DeleteVectorsByChunkIDs` → `DeleteByIDs` под одним `dao.DBTX`). В Rust LanceDB — отдельное хранилище без кросс-БД транзакций; строгая синхронность проектируется заново (D3).

## D1. Слои крейта и trait-контракт

**Решение:** `lib.rs` — trait `VectorIndex` (dyn-совместимый, Send+Sync) + `VectorIndexConfig` + `VectorsError`; `engine.rs` — LanceDB-реализация; `synx.rs` — формат фикстур vectors.bin. Крейт остаётся **tier-0 D1**: без внутренних зависимостей. На вход — готовые `(chunk_id, Vec<f32>)`; dim — параметр конфигурации, НЕ вызов embedding-крейта.
**Почему не альтернатива:** зависимость vectors→embedding сломала бы граф D1 (vectors — базовый ярус) и втянула бы ONNX в запросный путь (жёсткое ограничение «запросный путь не грузит модель»). Пересборка векторов из текста — оркестрация ingestion (будущий change).
**Референс:** заголовок `crates/vectors/src/lib.rs` (комментарий D1 tier 0); AGENTS.md таблица layout.

## D2. Sync-фасад над async LanceDB

**Решение:** trait-методы **sync**, как у `EmbeddingProvider` (конвенция embedding D9): `LanceEngine` владеет выделенным tokio `Runtime` (worker_threads=1–2) и через `block_on` исполняет async-API lancedb; вызывающий код (search/cli) dispatch-ит в `spawn_blocking`. Внутри `spawn_blocking`-потока вложенный `block_on` легален (мы вне async-контекста).
**Почему не альтернатива:** нативный `async fn` в trait (Rust 1.96 умеет) делает trait не-dyn-совместимым — потребители (search, mcp, cli) хотят `Arc<dyn VectorIndex>`; крейт `async-trait` — лишняя зависимость и стилистический разнобой с embedding. Полностью sync-движок без tokio невозможен: API lancedb целиком async.
**Риск:** двойной рантайм, если вызывающий код сам под tokio — документируется: вызывать только из `spawn_blocking`/синхронного контекста.
**Референс:** `.archive/spikes/src/bin/s3b_lance.rs` (протокол замера включал полный async-путь search→stream collect через tokio — overhead рантайма уже учтён в гейтах ADR 0003).

## D3. Каскадная согласованность SQLite ↔ LanceDB (решение человека 2026-08-21)

**Решение — трёхслойный протокол вместо невозможной кросс-БД транзакции:**
1. **Порядок каскада (контракт вызова):** при удалении чанков потребитель вызывает `delete_by_chunk_ids(...)` ДО удаления строк в SQLite. Анализ режимов сбоя: сбой после шага 1 → в SQLite нет чанка, в индексе осиротевший вектор (вычищается сверкой); обратный порядок дал бы «живой» чанк без вектора (тише деградирует поиск). Выбранный порядок делает ошибку видимой и машинно-обнаружимой.
2. **Толерантность потребителя:** поиск по индексу возвращает chunk_id; финальную фильтрацию по существованию чанка делает `search` (join против SQLite, будущий change) — осиротевший вектор не может попасть в ответ пользователю даже до GC.
3. **Примитивы reconciliation:** `chunk_ids()` (перечисление id индекса) + `count()`; сверка «индекс − SQLite → удалить» выполняется будущим GC-job'ом (scheduler), здесь даются только примитивы. Предельный ремонт — полная пересборка из текста чанков (`auto_rebuild_vectors` конфига, решение 2026-08-18).
**Почему не альтернатива:** outbox/журнал операций в SQLite ради псевдо-атомарности — лишняя схема и сложность для личного инструмента с recovery-пересборкой; двухфазный commit между SQLite и LanceDB недоступен.
**Референс:** `../synopsis/internal/gc/documents_gc.go` (FullClearDocByID шаг 5 — порядок «векторы → чанки» сохранён).

## D4. Движок и параметры — из ADR 0003 без отклонений

`lancedb = "0.37"` (lock 0.37.1 / lance 10.0.0), таблица: колонка `chunk_id u32` (PK-семантика на стороне приложения) + `vector FixedSizeList<Float32, dim>`; индекс `IvfHnswSq` M=16, efConstruction=100, num_partitions=256, метрика L2; поиск nprobes=32, efSearch=200 (оба — поля `VectorIndexConfig`, runtime-настройка по митигации ADR 0003 п.1). Запись стримингом Arrow RecordBatch'ами (num_rows_to_batch=1000). Исходные f32 — в таблице, квантизация только внутри индекса; ранжирование по `_distance`.
**Референс:** `docs/adr/0003-ann-engine.md` (таблица решения + измерения i8_ef200: p95 9.63/9.76 ms, recall 0.957/0.962, RSS ~71–79 MB на 250K).

## D5. Зависимости: обрезка фичей и feasibility-гейт

**Решение:** workspace-пин `lancedb = { version = "0.37", default-features = false }` (+ минимально необходимые фичи для локального filesystem-хранилища; облачные object-store'ы aws/azure/gcp/huggingface не нужны — один локальный бинарь). Точный состав фичей верифицируется по исходникам registry в задаче 1.1. До основной реализации — feasibility-гейт: host-сборка (MSRV транзитивных deps vs пин 1.96.0), спот-проверка cargo-zigbuild на windows-gnu и aarch64-apple-darwin, замер размера release-бинаря. Провал любого пункта — эскалация пользователю до задач движка (альтернатива — пересмотр ADR 0003, отдельное решение).
**Почему так:** единственный непроверенный риск ADR 0003 — тяжёлая транзитивная база (~250k строк: arrow/datafusion/object_store); снимается до того, как ИИ напишет модули против шва.

## D6. Формат SYNX (vectors.bin) — по design D4 native-seam-spikes

magic "SYNX" · version u32 LE = 1 · dim u32 LE · count u64 LE · rows `[u32 LE chunk_id][f32 LE × dim] × count` по возрастанию chunk_id. Reader — потоковый (итератор строк, без полной загрузки ~4 ГБ в RAM); writer — потоковый. Модуль `synx.rs` живёт в vectors (не в harness): harness — потребитель, а build-из-фикстуры — сценарий самого крейта. TODO в parity-harness закрывается использованием `vectors::synx`.
**Референс:** openspec/changes/archive/2026-08-18-native-seam-spikes/design.md D4.

## D7. Конфигурация: секция `vectors:` в preset (одобрено человеком 2026-08-21)

`VectorIndexConfig { dim=1024, m=16, ef_construction=100, num_partitions=256, nprobes=32, ef_search=200 }` определяется в крейте vectors. В config preset добавляется опциональная секция `vectors:` (serde default → дефолты ADR 0003). Это **аддитивное расширение замороженного config-format** — явное решение человека (2026-08-21, одобрение плана change'а): оракул ANN-параметров не имеет (vec0 brute-force настраивать нечем), неизвестные ключи Go игнорирует, пресеты без секции совместимы. Направление зависимости не нарушается: config::preset хранит сырые поля; маппинг в `VectorIndexConfig` — на wiring-уровне (cli/search, будущие change'и).
**Референс:** openspec/specs/config-format/spec.md («Неизвестные ключи не ломают старт»).

## D8. Бенчмарки и гейты

Два уровня:
1. **CI-гейт (сеть не нужна):** seeded синтетика умеренного масштаба (десятки тысяч × 1024, секунды прогона) — recall@10 ≥ 0.95 против in-process brute force, p95 < 10 ms, циклы персистентности/удаления. Гейты те же, что ADR 0003, но на меньшем N — smoke-уровень регрессии.
2. **Полный прогон (release-only, вручную/#[ignore]):** повтор протокола s3b_lance на реальной фикстуре vectors.bin (когда будет экспортирована оракулом) + синтетика N=1M — закрытие открытых вопросов ADR 0003 №2. Результаты — appendix к ADR 0003. Требует `--release`; debug-тайминги бессмысленны (урок спайка).
**Референс:** docs/adr/spike-s3-results.md (протокол: warmup 10, 100 held-out запросов, top-k=50, два прогона <5% разброса).

## Отклонения от оракула (осознанные)

- vec0 brute-force → LanceDB IvfHnswSq: контракт «top-k по L2» сохранён, механика заменена целиком (ADR 0003).
- Синхронность vec0-в-SQLite-транзакцией → трёхслойный протокол D3 (кросс-БД транзакций нет).
- `isNoSuchTable`-заглушки оракула (мягкая деградация при отсутствии sqlite-vec) не нужны: FTS5/vec0-класс проблем отсутствует, отсутствие индекса — явная ошибка.
