# Design: migrate-docs-site-to-rust

## Decisions

### D1: Copy the site verbatim as the scaffold (keep Docusaurus 3.10.2 + all UI)

**Decision.** Copy the old site directory wholesale into `site/` (excluding
`node_modules/`, `build/`, `.docusaurus/`, empty `scripts/`), keeping the
Docusaurus 3.10.2 framework, all 11 landing widgets, the shared UI kit, CSS
design tokens, client modules (cookie banner, navbar scroll), local search
plugin, and mermaid theme. Subsequent tasks rewrite content only.

**Why.** The user asked to *move* the site ("перенести сайт") and to keep the
design. The widgets/UI kit/CSS are a working, reviewed design investment; the
build was green in the old project, so a verbatim copy starts from a known-good
state.

**Revision (2026-09-05, user decision).** `package-lock.json` is copied to
disk for local builds but intentionally NOT committed (gitignored): the
inherited lockfile's `resolved` URLs point at a private LAN mirror
(`http://nexus.lan:3080`), which would break `npm ci` off-LAN. Installs use
`npm install`.

**Alternative rejected.** Rebuilding a fresh Docusaurus instance or migrating to
another framework (VitePress/Astro) would discard the design and require
re-validating every widget; the user explicitly chose to keep Docusaurus 3.10.2.

### D2: The contract specs are the single source of truth for content

**Decision.** Every content page is written against named reference files:
the 14 contract specs (`openspec/specs/{mcp-contract,cli-surface,data-schema,
config-format,db-storage,embedding,entity-extraction,hybrid-search,
knowledge-graph,llm-client,parsing-and-chunking,pipeline,vector-index,
utils}/spec.md`), `README.md`, `AGENTS.md`, `docs/adr/`,
`.github/workflows/{ci,release}.yml`, `workspace/configs/README.md`. Each task
body names the exact references the agent must read before writing.

**Why.** The old docs describe the Go implementation and are factually wrong
for the Rust binary in ~every reference area (CLI, storage, vector engine,
CI, build). The specs pin the behavior as-is; writing from them guarantees
documentation parity.

**Alternative rejected.** Patching the old docs in place — the Go-era facts
are pervasive (sync, CGO, vec0, single DB, GitHub Actions, Docker); patching
leaves wrong facts and requires a full diff of the old implementation anyway.

### D3: Full rewrite, not a patch; add/delete pages freely

**Decision.** Rewrite every doc page and every landing widget's content;
create 8 new pages; delete `developer/docker.mdx`.

**Why.** User decision ("Можно менять всё: дополнять, удалять, создавать новые
страницы"). The new pages cover functionality that did not exist in the Go
version (job queue, double MCP transport, cache DB, vector rebuild, Gitea
releases, ADRs, OpenSpec workflow, workspace layout).

### D4: Green build at every task boundary

**Decision.** Every task ends with `npm run typecheck` (0 errors) and
`npm run build` (success) passing in `site/`. `onBrokenLinks: 'throw'` fails
the build on any broken internal link, so the site is always link-consistent.
The sidebar is autogenerated from the docs folder structure
(`sidebars.ts` → `autogenerated`), so adding/deleting pages needs no manual
sidebar edit; page order is set via frontmatter `sidebar_position`.

**Why.** Broken links are the main mechanical risk of a full rewrite; checking
per task localizes failures to the task that introduced them.

**Alternative rejected.** One big rewrite with a single final build — broken
links and content errors accumulate and are hard to attribute.

### D5: Manual deployment; GitHub links; Metrika kept

**Decision.**
- `url`: `https://synopsis-memex.tekblueprint.org` (the user's site).
- Remove the GitHub Pages deploy fields (`organizationName`, `projectName`).
- `editUrl` → `https://github.com/devmix/synopsis-rs/edit/main/site/docs/`
  (Docusaurus appends the doc's relative path).
- Navbar + footer GitHub links → `https://github.com/devmix/synopsis-rs`.
- Keep the Yandex.Metrika counter, Google Fonts, cookie banner, local search,
  mermaid, and prism themes (user decision: Metrika stays).
- No site build in CI (user decision).

**Why.** The user deploys manually to their own site; the public repo URL is
the GitHub mirror (`github.com/devmix/synopsis-rs`), per user decision.

**Alternative rejected.** Keeping the GitHub Pages config — it points at the
old repo (`devmix/synopsis`) and would deploy the wrong site; Gitea Pages —
the user deploys manually and the public link surface is GitHub.

### D6: 8 new pages

**Decision.** New pages, each with its spec reference:

| Page | Location | Documents |
|---|---|---|
| Workspace Layout | `docs/concepts/workspace-layout.mdx` | `workspace/` tree, per-dataset state, cache DB, models/onnxruntime dirs (AGENTS.md data layout) |
| Job Queue | `docs/concepts/job-queue.mdx` | `document_jobs` table, worker, startup reconcile, watcher enqueue, `queue status|reset-retries` (data-schema, cli-surface, pipeline) |
| Vector Rebuild | `docs/concepts/vector-rebuild.mdx` | vectors rebuilt from chunk text; usearch index; dimension-mismatch clear-then-queue (vector-index) |
| Cache DB | `docs/concepts/cache-db.mdx` | global `workspace/db/cache/cache.db`: embedding + LLM caches (db-storage, embedding) |
| MCP Transport | `docs/concepts/mcp-transport.mdx` | double transport: Streamable HTTP `/mcp` + legacy SSE `/sse`+`/message` + `/health` (mcp-contract) |
| Gitea Releases | `docs/developer/gitea-releases.mdx` | v*-tag release workflow, 5-target zigbuild, archive contents (release.yml) |
| ADRs | `docs/developer/adrs.mdx` | summaries of ADRs 0001–0004 + links to `docs/adr/` |
| OpenSpec Workflow | `docs/developer/openspec-workflow.mdx` | proposal→design→specs→tasks→apply→archive, frozen contracts, opsx commands (openspec/config.yaml) |

**Why.** These are the functional deltas old→new that have no counterpart in
the old site; D3 requires the site to document the new functionality.

### D7: Delete `developer/docker.mdx`

**Decision.** Remove the Docker page entirely; no Docker references remain in
the developer docs.

**Why.** Docker documented the Go-era CGO multi-stage build. The Rust binary
builds natively (static musl, zigbuild cross-compilation); there is no Docker
support to document.

### D8: Task split for agent context + 500-line cap; two site agents

**Decision.** 20 tasks (1.1–1.20), each scoped to 1–3 files, each body
self-contained (goal, exact file scope, dependencies, machine-checkable
acceptance, named references). Implementation agents (copied from the old
project into `.opencode/agents/`, adapted Go→Rust; `.opencode/` is gitignored
— local workflow files only):

- **site-implementer** — site code: `docusaurus.config.ts`, widgets, CSS, MDX
  mechanics, deletions.
- **docs-writer** — MDX documentation content.

**Why.** `openspec/config.yaml` execution model: fresh agent per task, ~100k
context budget, final diff ≤ ~500 lines. `rust-implementer` is the wrong stack
(cargo gates, Rust workspace tasks).

**Alternative rejected.** One agent for the whole site — exceeds the context
budget and the 500-line task cap by an order of magnitude.

### D9: Final parity audit + Go-era residue sweep

**Decision.** Task 1.20 runs the final audit: `npm run typecheck` +
`npm run build` green; a Go-era residue sweep
(`git grep -in 'golang\|cgo\|sqlite-vec\|vec0\|mcp-go\|goreleaser\|golangci\|
go test\|go build' -- site/docs site/src` → 0); no `sync` subcommand mentions;
a per-spec checklist covering all 14 specs; the 12 MCP tool pages cross-checked
against `mcp-contract/spec.md`; roadmap rewrite; architecture SVG updates.

**Why.** The per-task checks are local; the audit is the global guarantee that
the finished site matches the implementation.

### D10: Concept pages stay conceptual; schema details live in reference/developer docs

**Decision.** (User directive, 2026-09-05, during task 4.2.) Concept pages
(`site/docs/concepts/`) describe the WHAT and WHY at the model level: how the
pieces fit together, the behavior a user/operator observes, the invariants.
They do NOT dump purely technical schema details — table names with column
lists and types, index names, migration file paths, `CREATE TABLE` mechanics.
Those belong to `reference/database-schema.mdx` (task 7.2: every table with
columns, constraints, indexes per the data-schema + db-storage specs) and the
developer docs (task 5.2 migrations). A passing prose mention of a table or
column name for context is fine; a schema table is not.

**Why.** The user reviews the site as documentation: concepts should read for
understanding, not as a schema reference. The full schema is already covered
by task 7.2, so nothing is lost by keeping it out of concepts.

**Consequence.** Task 4.2's `cache-db.mdx` is revised to the conceptual level
(the persistent LLM/NER decision caches vs the in-memory embedding cache,
graceful degradation — no column tables). Task 4.1's `job-queue.mdx` (the
11-column `document_jobs` table) is the same pattern and is a candidate for
the same slimming (fix-forward) — pending user decision. Task 7.2's Cache DB
line is corrected: the cache DB holds `llm_ner_cache`, `llm_linker_cache`,
`app_kv` (per `db-storage/spec.md` + `migrations/cache/1-init/up.sql`); the
embedding cache is in-memory (per `embedding/spec.md`).
