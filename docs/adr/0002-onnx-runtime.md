# ADR 0002 — ONNX Runtime шов в Rust (ort, load-dynamic)

**Статус:** GO по шву; все критерии задачи 2.1 выполнены для ВСЕХ трёх моделей реестра onnx.yaml (спайк `s2_onnx` завершается кодом 0).
**Дата:** 2026-08-18 · **Change:** native-seam-spikes, задача 2.1 (спайк S2: `crates/spikes/src/bin/s2_onnx.rs`; расширено на все 3 модели реестра — Ревизия 2 задачи)

## Вопрос

Может ли Rust-бинарь владеть полным путём «загрузка ONNX Runtime → эмбеддинги ВСЕХ моделей реестра onnx.yaml» без build-time скачивания и без внешних сервисов: динамическая загрузка `.so` из локального `data/` по onnx.yaml-реестру, pipeline токенизации/инференса, и детерминированные N=50 вектора (dim 1024/384/384) для каждой из трёх моделей: `bge-m3-int8`, `bge-small-en-v1.5` (default реестра и config.default.yaml), `paraphrase-multilingual-MiniLM-L12-v2`? Какой механизм биндингов зафиксировать для боевого crate'а `embedding`?

## Варианты

1. **ort (pykeio) 2.x, `load-dynamic` + `api-28`, default-features выключены** — ORT не скачивается и не линкуется на этапе сборки; `.so` открывается через dlopen в рантайме из пути, резолвленного по onnx.yaml. C API level 28 = ORT 1.28 ровно та версия, которую declares onnx.yaml-реестр.
2. **onnxruntime-rs** — frozen entry из openspec/config.yaml; нерезолвябелен: crate с таким именем на crates.io не существует (последняя публикация — мёртвая 0.2.x под старое API), преемник `ort` стабильного релиза ещё не имеет. Пин фиксирован как `ort = "2.0.0-rc.13"`.
3. Собственный FFI поверх libonnx (ручные `extern "C"` + raw pointers) — отклонено: дублирует то, что ort уже даёт типобезопасно (Tensor/Session/DynValue), при этом теряет проверенную обработку ошибок и memory ownership; rc-качество API ort компенсируется тем, что шов узкий (1 сессия, 3 тензора).
4. Sidecar-процесс: вынос эмбеддингов в отдельный бинарь по IPC — отклонено: нарушает контракт «один локальный бинарь», добавляет процессный overhead к каждому тексту и делает parity-тесты зависимыми от внешнего процесса.

## Решение (GO)

Шов доказан: Rust владеет полным путём эмбеддингов через ORT 1.28, загружаемую динамически из локального `data/`. **Вердикт: GO** — crate `embedding` строится на:

- пин биндингов: `ort = { version = "2.0.0-rc.13", default-features = false, features = ["load-dynamic", "api-28"] }`;
- механизм артефактов — onnx.yaml-реестр (download URL + size_bytes + sha256-verify); путь хранения и resolve-логика — `data/` внутри репо (см. data/README.md);
- batch size = 1 на текст (батчинг — задача боевого crate'а `ingestion`, см. «Открытые вопросы»);
- pipeline: `encode(text, add_special_tokens=false)` → truncate до 512 → right-pad id **0** (padID остаётся нулевым — аномалия tokenizer.json) → `attention_mask = [1]×512` → входные тензоры привязываются в каноническом порядке `input_ids, attention_mask, token_type_ids` только если объявлены графом (у bge-m3-int8 нет token_type_ids; у остальных двух моделей — есть) → выход по приоритету: `sentence_embedding` (bge-m3-int8), иначе `last_hidden_state`, иначе единственный объявленный output (CLS-вектор [0,0,:] для last_hidden_state) → L2-нормализация в f64, каст обратно в f32.

### Deviation пина биндингов (объяснение, прецедент ADR 0001)

Замороженный entry «onnxruntime-rs» в openspec/config.yaml **нерезолвябелен** дословно: crate с этим именем на crates.io не существует. Реальный пин — `ort` (преемник, pykeio), версия 2.0.0-rc.13 как единственная резолвябельная под C API level 28 (= ORT 1.28). Намерение frozen entry (ORT 1.28, динамическая загрузка, без build-time скачивания) сохранено полностью; текст config.yaml не редактируется — отклонение зафиксировано здесь и в ревизии задачи 2.1.

## Отклонённые альтернативы (см. «Варианты»)

- **onnxruntime-rs** — не существует на crates.io (пункт 2).
- **Собственный FFI** — дублирование функциональности ort без выигрыша; узость шва делает rc-API приемлемым (пункт 3).
- **Sidecar-процесс для эмбеддингов** — нарушает «один локальный бинарь» и контракт parity (пункт 4).

## Открытые вопросы (передаются в последующие задачи)

- **~1 с/текст (bge-m3-int8) при batch size 1; ~0.12 с/текст для двух 384-dim моделей.** Путь запроса модель эмбеддингов НЕ загружает — жёсткое ограничение openspec/config.yaml (context, «Жёсткие ограничения»), поэтому задержка касается только ingestion/reindex; боевой crate `ingestion` должен батчить инференс и/или ограничивать параллелизм (ORT сам мультипоточен).
- **Peak RSS по моделям: ≈3.1 ГБ (bge-m3-int8), ≈2.4 ГБ (MiniLM-L12, float-веса), ≈0.8 ГБ (bge-small)** при бюджете ноутбука 16 ГБ — совместимо, но фаза инференса не должна перекрываться по времени с тяжёлыми ANN-операциями; RAM-бюджет и требование disk-backed/квантованного индекса — из «Жёстких ограничений» openspec/config.yaml.
- **Стабилизация ort.** Прогон на rc.13; перед боевым crate'ом `embedding` повторить проверку резолва (возможна новая rc) — механизм шва от версии не зависит.
