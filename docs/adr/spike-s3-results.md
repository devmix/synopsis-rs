## Корпус и ground truth

- N = **250 000** × 1024-dim f32; seeded синтетика: гауссова смесь K=256 центров на единичной сфере, per-dim σ=0.1, ре-нормализация; PRNG SplitMix64 + Box-Muller, seed `0x5EED_3B25_CAFE_BAB7` (зашит в бинарь).
- 100 held-out запросов из того же распределения (отдельный сегмент seed'а), top-k = 50.
- Ground truth — exact L2² brute force внутри спайка (rayon, 16 workers); ~5 c на прогон.
- **Fingerprint детерминизма** (совпадает во ВСЕХ прогонах: run-1, A, B и всех diagnostic): `corpus_fnv1a=50194a997027c6d2 first_query_head=[0.010096, -0.003417, -0.064351, 0.021204]`.
- Фиксированные параметры всех конфигураций: **M=16, efConstruction=100, num_partitions=256 (IVF), nprobes=32, L2**. Варьируются только квантизация и efSearch.

## Диагностика: sweep nprobes × efSearch (на индексах прогонов B)

`--reuse <cfg> --nprobes N --ef E` — поиск без пересборки индекса. Матрица 2 квантизации × nprobes {64,128,256} × efSearch {50,200}:

| i8 | 64 | 200 | 8.119 | 10.334 | 0.960 | 430 |
| i8 | 128 | 50 | 8.067 | 10.790 | 0.888 | 438 |

Чтение: (1) **efSearch доминирует по recall** — при ef=50 потолок ~0.88–0.90 независимо от nprobes; ef=200 даёт 0.96–0.997. (2) Рост nprobes с 32→256 поднимает recall на +~1–4 pp, но линейно растит p95 — ни одна точка sweep'а не превосходит протокольную i8_ef200 по совокупности гейтов. (3) i8 ≈ в 3 раза быстрее f32 при потере ~0.7–3 pp recall (шум квантизации).

## Примечания к методике

- **Фикс бага recall до валидных прогонов:** первая версия считала recall через `binary_search` по id-срезу, отсортированному по расстоянию ANN-результата (НЕ по значению id) — давал ложный ~0.19–0.22 во всех конфигах. Фикс: `.contains()` + явная сортировка результатов по `_distance` до take(10). Валидация фикса: full-coverage диагностика (nprobes=256, ef=200) подняла recall f32 с 0.219 → 0.997. Все цифры выше — ПОСТ-фикс, на зафиксированном бинарии; протокольные A/B выполнены последовательно на нём же.
- **RSS-delta** = пик RSS процесса поиска минус RSS до открытия индекса (peak RSS из `/proc/self/status` во время 100 запросов). Включает mmap'ы lance, но не полный объём файла при `mmap_size` — реальное давление на RAM ноутбука меньше размера таблицы.
- **total bytes** = таблица + индекс в work-dir (data/ + `_indices/`). Для i8: ~1.32 ГБ на 250K×1024 → экстраполяция на N=1M ≈ 5.3 ГБ на диске (RAM — см. RSS-delta).
- **Warmup** = 10 запросов перед замером; тайминг каждого из 100 зачётных запросов — `Instant` вокруг полного async-пути (search → collect stream).
