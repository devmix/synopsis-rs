# Database Schema

All state lives in a **single SQLite file** (default `./data/knowledge.db`), with FTS5 full-text index and sqlite-vec vector index compiled into the binary via CGO. A separate small `cache.db` file holds embedding/result caches (path: `database.cache_path` or beside the main file).

At startup, SQL migrations from `paths.migrations_dir` (default `migrations/`) are applied **in filename order**, each in its own transaction. Applied versions are tracked in `_schema_migrations`. After the core migrations, the vec0 vector table is initialized with the configured embedding dimension.

## Migrations

| File | Purpose |
|---|---|
| `001_schema.sql` | Complete core schema: all base tables, indexes, the FTS5 virtual table, and its synchronization triggers. (Consolidates the original schema history; later columns such as `documents.content_hash` and `facts.weight` are defined inline.) |
| `002_dedup.sql` | Data migration: deletes duplicate `documents` rows (keeps the highest `id` per `original_path`) and creates the unique index `idx_documents_original_path`. |
| `003_drop_documents_domain.sql` | Drops `idx_documents_domain` and the `documents.domain` column. The column was never reliably populated; the `metadata_json` field `$.domain` is the single source of truth for document domains. |
| `004_extracted_at_backfill.sql` | Backfills `fact_sources.extracted_at` for zero/empty timestamps using the last ingest time (`MAX(updated_at)` from `documents`, falling back to `facts`, then `NOW()`). |
| `005_app_kv.sql` | Creates the `app_kv` key-value store for application-level state (e.g. the `last_linking_run` timestamp). |

The vec0 table (`chunks_vec`) is **not** a migration: it is created (or dimension-validated) by the database layer after the migrations, because its column type depends on the configured `vector_dim` — see [Vector index (vec0)](#vector-index-vec0).

## Full-text index (FTS5)

`chunks_fts` is an FTS5 **external-content** virtual table over `chunks`:

```sql
CREATE VIRTUAL TABLE chunks_fts USING fts5(
    chunk_text,
    content='chunks',
    content_rowid='id'
);
```

Three triggers keep it in sync with `chunks`:

| Trigger | Fires | Action |
|---|---|---|
| `chunks_fts_ai` | AFTER INSERT ON `chunks` | Inserts the new row's text into the FTS index |
| `chunks_fts_ad` | AFTER DELETE ON `chunks` | Removes the old row from the FTS index |
| `chunks_fts_au` | AFTER UPDATE ON `chunks` | Remove + re-insert, so updated text is re-indexed |

Lexical search is an FTS5 `MATCH` query scored with BM25 (see [Hybrid Search](../concepts/hybrid-search.mdx)).

## Vector index (vec0)

`chunks_vec` is a sqlite-vec virtual table, created at startup by the database layer (after the SQL migrations) with the **configured** embedding dimension:

```sql
CREATE VIRTUAL TABLE chunks_vec USING vec0(
    chunk_id INTEGER PRIMARY KEY,
    vector FLOAT[N]   -- N = configured embeddings vector_dim
);
```

- Semantic search is a KNN query over `vector`, returning `distance` (cosine) per row.
- On startup the layer parses the existing table's `FLOAT[N]` declaration. If `N` differs from the configured dimension, a **dimension mismatch error** is raised; recovery is `--auto-rebuild-vectors`, `embeddings.auto_rebuild_vectors`, or deleting the database / dropping `chunks_vec` and re-ingesting. See [Troubleshooting](../guides/troubleshooting.mdx#embedding-dimension-mismatch).
- Orphan rows in `chunks_vec` (vectors whose chunk no longer exists) are removed by the `orphan_cleanup` job and during rebuild.

## PRAGMAs

Connection-level settings applied on every open (see also [Configuration Schema — PRAGMAs](./config-schema.mdx#pragmas-applied-on-connection)):

`journal_mode=WAL`, `synchronous=NORMAL`, `cache_size=-64000` (64 MB), `mmap_size=268435456` (256 MB), `foreign_keys=ON`, plus a DSN `busy_timeout=5000`.
