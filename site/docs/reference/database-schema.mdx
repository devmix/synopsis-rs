# Database Schema

Synopsis keeps **two SQLite databases** plus **vector index files outside SQLite**:

| Artifact | Location | Scope |
|---|---|---|
| **Knowledge DB** | `<workspace>/datasets/<name>/state/db/knowledge.db` | One per dataset: documents, chunks, entities, facts, links, the job queue |
| **Cache DB** | `<workspace>/db/cache/cache.db` | One global, shared by all datasets: LLM response caches and run markers |
| **Vector index** | `<workspace>/datasets/<name>/state/vectors/usearch/` | One per dataset: the usearch HNSW index files (see [Vectors live outside SQLite](#vectors-live-outside-sqlite)) |

The layout is part of the [Workspace Layout](../concepts/workspace-layout.mdx).

## Migrations and schema state

- Each database is created by a **single squashed init migration** — `migrations/knowledge/1-init/up.sql` for the knowledge DB, `migrations/cache/1-init/up.sql` for the cache DB — embedded into the binary at compile time (`include_dir!` in `crates/db`).
- `PRAGMA user_version` is the **sole source of truth** about the schema state (`= 1` after init). The `_schema_migrations` tracking table is **deliberately NOT created**.
- Migrations are applied at startup, are idempotent (`IF NOT EXISTS`), and a subsequent startup is a no-op. Future migrations are numbered directories `<id>-<slug>/up.sql`, forward-only (no down.sql); shipped migrations are never edited.
- A pre-existing `knowledge.db` is **NOT opened and NOT migrated**: the Rust binary always builds its database from scratch, and data is never migrated.

See [Migrations](../developer/migrations.mdx) for the full migration discipline.

## Knowledge DB tables

### `documents`

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Document ID. |
| `source_type` | TEXT | NOT NULL | `'json'`, `'markdown'`, `'steam'`, `'unstructured'`, … |
| `original_path` | TEXT | NOT NULL, UNIQUE (`idx_documents_original_path`) | Path of the source file. |
| `metadata_json` | TEXT | | JSON metadata; `$.domain` is the canonical domain array (e.g. `["hr","policy"]`). |
| `content_hash` | TEXT | | Content hash for change detection on re-ingestion. |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Insertion time. |
| `updated_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Last re-ingestion time. |

### `chunks`

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Chunk ID. |
| `doc_id` | INTEGER | NOT NULL, FK → `documents.id` ON DELETE CASCADE | Owning document. |
| `chunk_text` | TEXT | NOT NULL | The pure source slice; the byte-offset invariant `content[start_offset..end_offset] == chunk_text` holds. |
| `sequence_num` | INTEGER | NOT NULL | Chunk order within the document. |
| `start_offset` | INTEGER | | Byte offset of the chunk start in the original text (nullable). |
| `end_offset` | INTEGER | | Byte offset of the chunk end (nullable). |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Insertion time. |
| `search_text` | TEXT | NOT NULL DEFAULT `''` | The search-oriented text: for Markdown chunks the heading breadcrumb (multi-line heading path) followed by the chunk body, or the body alone when there is no breadcrumb. **Both search legs (FTS5 lexical + vector semantic) operate on `search_text`, not `chunk_text`.** |
| `metadata_json` | TEXT | nullable, no default | Per-chunk metadata bag as raw JSON (`section_title`, `heading_level`, `breadcrumb`, `image_paths`, …); `NULL` means "no chunk metadata". Parsed on demand. |

### `entities`

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Entity ID. |
| `type` | TEXT | NOT NULL | Entity type (e.g. `employee`, `department`, `policy`, `system`). |
| `name` | TEXT | NOT NULL | Entity name. |
| `domain` | TEXT | NOT NULL DEFAULT `''` | Domain this entity belongs to. |
| `description` | TEXT | | Free-text description. |
| `confidence` | FLOAT | | Extraction confidence. |
| `metadata_json` | TEXT | | JSON metadata. |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Insertion time. |

Unique constraint: `(type, name, domain)` — deduplication works by resolving names, then upserting within this key.

### `chunk_entities`

Maps chunks to the entities extracted from them.

| Column | Type | Constraints |
|---|---|---|
| `chunk_id` | INTEGER | NOT NULL, FK → `chunks.id` ON DELETE CASCADE |
| `entity_id` | INTEGER | NOT NULL, FK → `entities.id` ON DELETE CASCADE |

Primary key: `(chunk_id, entity_id)`.

### `facts`

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Fact ID. |
| `subject_entity_id` | INTEGER | FK → `entities.id` (nullable) | Subject entity. |
| `predicate` | TEXT | NOT NULL | Relation predicate. |
| `object_entity_id` | INTEGER | FK → `entities.id` (nullable) | Object entity. |
| `domain` | TEXT | NOT NULL DEFAULT `''` | Domain this fact belongs to. |
| `metadata` | TEXT | | JSON metadata (e.g. `threshold_amount`, `condition`). |
| `status` | TEXT | NOT NULL DEFAULT `'draft'`, CHECK `('draft','pending','approved','rejected')` | Lifecycle status. **Only `approved` facts appear in search expansion and entity dossiers.** |
| `valid_from` | DATE | | Temporal validity start. |
| `valid_to` | DATE | | Temporal validity end. |
| `weight` | INTEGER | NOT NULL DEFAULT 1 | Weight used in relation traversal. |
| `created_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Insertion time. |
| `updated_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Last status/metadata change. |

Unique constraint: `(subject_entity_id, object_entity_id, predicate)`.

### `fact_sources`

Provenance: the source quotes for each fact.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | |
| `fact_id` | INTEGER | NOT NULL, FK → `facts.id` ON DELETE CASCADE | |
| `document_id` | INTEGER | NOT NULL, FK → `documents.id` ON DELETE CASCADE | Source document. (Deliberate deviation from the v5 schema, where this column was `TEXT`.) |
| `quote` | TEXT | | Exact quote from the source. |
| `extracted_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP | Extraction time. |

### `entity_sources`

Documents that mention each entity.

| Column | Type | Constraints |
|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT |
| `entity_id` | INTEGER | NOT NULL, FK → `entities.id` ON DELETE CASCADE |
| `document_id` | INTEGER | NOT NULL, FK → `documents.id` ON DELETE CASCADE |

Unique constraint: `(entity_id, document_id)`.

### `entity_links`

Cross-domain entity links created during ingestion (see [Cross-Domain Linking](../concepts/cross-domain-linking.mdx)).

| Column | Type | Constraints | Description |
|---|---|---|---|
| `subject_entity_id` | INTEGER | NOT NULL, FK → `entities.id` ON DELETE CASCADE | |
| `target_entity_id` | INTEGER | NOT NULL, FK → `entities.id` ON DELETE CASCADE | |
| `relation_type` | TEXT | NOT NULL DEFAULT `'same_entity'` | |
| `method` | TEXT | NOT NULL | How the link was established: `rule` (CEL expression), `equals`, or `llm`. |
| `confidence` | FLOAT | NOT NULL DEFAULT 1.0 | Link confidence. |
| `evidence` | TEXT | | Supporting evidence text. |

Primary key: `(subject_entity_id, target_entity_id, relation_type)`. Check constraint: `subject_entity_id != target_entity_id`.

### `queue_tasks`

The generic event queue — the single state machine the file watcher, the startup reconcile, the pipeline, and the background worker all enqueue into (see [Job Queue](../concepts/job-queue.mdx)). One row per `(type, identity)`, covering document operations (`doc:index`, `doc:delete`) and entity-linking tasks (`entity:link`).

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Row id; the claim-order tie-breaker. |
| `type` | TEXT | NOT NULL | Event type: `doc:index`, `doc:delete`, or `entity:link`. |
| `identity` | TEXT | NOT NULL | Dedup key: the document path for `doc:*` events, the document id (decimal string) for `entity:link`. |
| `event` | TEXT | NOT NULL | JSON residual payload (`source_path`/`content_hash` or `entity_ids`). |
| `status` | TEXT | NOT NULL DEFAULT `'pending'` | `'pending'` → `'processing'` → `'done'` or `'error'`. |
| `attempts` | INTEGER | NOT NULL DEFAULT 0 | Attempts so far. |
| `max_attempts` | INTEGER | NOT NULL DEFAULT 3 | Retry limit (driven by `ingestion.max_retries`). |
| `last_error` | TEXT | | Last failure message. |
| `next_attempt_at` | INTEGER | NOT NULL DEFAULT 0 | Unix-seconds due time for the next attempt (also the re-enqueue "move to end" lever). |
| `created_at` | INTEGER | NOT NULL | Unix seconds. |
| `updated_at` | INTEGER | NOT NULL | Unix seconds. |

### `usearch_vectors_log`

Write-ahead log for the usearch ANN engine (ADR 0004). It records **operations**, never vector payloads — the rebuild re-encodes chunk text, so the payloads live in `chunks`.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `segment_id` | INTEGER | NOT NULL (composite PK) | The segment the operation applies to; `0` means "current/RAM operations". |
| `chunk_id` | INTEGER | NOT NULL (composite PK) | The affected chunk. |
| `flags` | INTEGER | NOT NULL | Operation bitmask: `1` = ADD, `2` = DEL, `4` = UPD. |
| `created_at` | TEXT | NOT NULL | Timestamp. |

Primary key: `(segment_id, chunk_id)`.

## Full-text index (FTS5)

`chunks_fts` is an FTS5 **external-content** virtual table over `chunks`, indexed on **`search_text`** (not `chunk_text`):

```sql
CREATE VIRTUAL TABLE chunks_fts USING fts5(
    search_text,
    content='chunks',
    content_rowid='id'
);
```

Three triggers keep it in sync with `chunks`:

| Trigger | Fires | Action |
|---|---|---|
| `chunks_fts_ai` | AFTER INSERT ON `chunks` | Inserts the new row's `search_text` into the FTS index |
| `chunks_fts_ad` | AFTER DELETE ON `chunks` | Removes the old row from the FTS index |
| `chunks_fts_au` | AFTER UPDATE ON `chunks` | Remove + re-insert, so updated text is re-indexed |

The FTS5 engine is compiled into the bundled SQLite — no external extension. Lexical search is an FTS5 `MATCH` query scored with BM25, optionally filtered by domain via `json_each` (see [Hybrid Search](../concepts/hybrid-search.mdx)).

## Cache DB

One global database at `<workspace>/db/cache/cache.db`, shared by **all** datasets and holding only cache data (see [Cache Database](../concepts/cache-db.mdx)). It is fully independent of the knowledge DBs: clearing or rebuilding a dataset has zero effect on the cache, and the cache outlives every dataset it has served.

### `llm_ner_cache`

Cached LLM NER responses — a repeat request for the same text with the same call parameters is a local hit instead of a network call.

| Column | Type | Constraints |
|---|---|---|
| `cache_key` | TEXT | PRIMARY KEY |
| `result` | TEXT | NOT NULL |

### `llm_linker_cache`

Cached cross-domain linker decisions — re-linking a fresh knowledge DB reuses every prior decision.

| Column | Type | Constraints |
|---|---|---|
| `cache_key` | TEXT | PRIMARY KEY |
| `decision` | TEXT | NOT NULL |

### `app_kv`

Generic key-value run markers (e.g. the `last_linking_run` timestamp that bounds the window of entities considered by the next incremental run).

| Column | Type | Constraints |
|---|---|---|
| `key` | TEXT | PRIMARY KEY |
| `value` | TEXT | |
| `updated_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP |

### The embedding cache (in-memory)

The embedding cache is **NOT a table** — it lives in memory, per process. It is keyed by model name + dimensionality + text and is size-limited (default 10,000 entries, thread-safe): a repeat request for the same text with the same model returns the cached vector without re-inference. It vanishes when the process exits; cross-run no-re-embedding comes from the job queue's content-hash dedup instead (see [Model Management](../guides/model-management.mdx#the-embedding-cache-in-memory)).

## Vectors live outside SQLite

Embedding vectors are **not stored in either database**. The semantic leg of search queries the **usearch HNSW index** — disk-backed (mmap), scalar-quantized (bf16 default), two-layer persistence (RAM layer + WAL segments + compaction) — stored as index files under the dataset's `state/vectors/usearch/` directory (see [Vector Rebuild](../concepts/vector-rebuild.mdx)).

- The index is **rebuilt from the chunk text** in `chunks`; the old vector data in pre-existing files is never read or migrated.
- The index dimensionality must match the embedding model from the configuration; a mismatch triggers the clear-then-queue behavior (`serve --auto-rebuild-vectors` or `embeddings.auto_rebuild_vectors` to rebuild automatically).
- `usearch_vectors_log` in the knowledge DB is the engine's **operations** log (segment/chunk/flags), not the vector payloads.
- Orphan entries (vectors whose chunk no longer exists) are removed by the `orphan_cleanup` job and during rebuild.

## PRAGMAs

Connection-level settings applied on every pooled connection (see also [Configuration Schema — PRAGMAs](./config-schema.mdx#pragmas-applied-on-connection)):

`journal_mode=WAL`, `synchronous=NORMAL`, `cache_size=-64000` (64 MB), `mmap_size=268435456` (256 MB), `foreign_keys=ON`, `busy_timeout=5000`.
