# CLI Reference

The `synopsis` binary uses **subcommand dispatch**. Global flags must appear **before** the subcommand; each subcommand then has its own flags.

```
synopsis [--config PATH] [--preset NAME] [--dataset NAME] [--version] <subcommand> [flags...]
```

| Subcommand | Purpose |
| --- | --- |
| `serve` | Start the MCP server (startup reconcile + file watching + background job worker) |
| `queue status \| reset-retries` | Inspect and repair the event task queue |
| `db stats \| clear \| merge-entities` | Dataset statistics / delete the entire dataset state / merge one entity into another |
| `model list \| download \| delete \| info \| benchmark [NAME]` | Manage embedding models |
| `onnx-runtime install \| status \| uninstall` | Manage the ONNX Runtime library |
| `load-test` | Fill the database with synthetic data and benchmark all MCP tool handlers |

Running the binary with no subcommand (or with an unknown subcommand) prints usage on stderr and exits with code `1` (the binary overrides the usual argument-parser exit code `2` for usage errors).

## Global flags

| Flag | Description |
| --- | --- |
| `--config PATH` | Path to the configuration file, used verbatim (skips auto-search) |
| `--preset NAME` | Configuration preset name; the binary searches for `config.{NAME}.yaml` (default: `default`) |
| `--dataset NAME` | Dataset name; overrides `dataset.name` from the config |
| `--version` | Print `synopsis <version>` and exit `0` |

```bash
# Use an explicit config and point at a specific dataset
synopsis --config workspace/configs/config.default.yaml --dataset edtech serve

# A custom preset
cp workspace/configs/config.default.yaml workspace/configs/config.prod.yaml
synopsis --preset prod serve
```

## Config path resolution

When `--config` is not given, the effective path is `config.{preset}.yaml` (default preset: `default`), searched in this exact order:

1. `<exeDir>/workspace/configs/config.{preset}.yaml`
2. `<exeDir>/config.{preset}.yaml`
3. `<parent(exeDir)>/config.{preset}.yaml`
4. `<parent(exeDir)>/workspace/configs/config.{preset}.yaml`
5. `<CWD>/workspace/configs/config.{preset}.yaml`
6. `<CWD>/config.{preset}.yaml`

In short: `<exeDir>/workspace/configs/` → parent directory → CWD. The executable path is not symlink-resolved. If none of the candidates exists, the binary falls back to the relative `workspace/configs/config.{preset}.yaml` and fails with a load error naming that path.

## `serve`

The only long-running mode: a startup reconcile (the diff of changed sources is enqueued into the event task queue), the MCP server over HTTP, and a file watcher (changed sources are enqueued again). A background worker processes the queue.

```
synopsis serve [--no-initial-sync] [--port N] [--auto-rebuild-vectors]
```

| Flag | Default | Description |
| --- | --- | --- |
| `--no-initial-sync` | `false` | Skip the startup reconcile (the initial full source scan) |
| `--port N` | `8080` (the `server.port` config value) | HTTP listen port; overrides `server.port` from the config |
| `--auto-rebuild-vectors` | `false` | Automatically rebuild vectors on an embedding dimension mismatch |

Endpoints on the configured `server.host:server.port` (default `0.0.0.0:8080`):

- `/mcp` — MCP over Streamable HTTP (the primary transport)
- `GET /sse` + `POST /message?sessionId=` — legacy HTTP+SSE transport
- `GET /health` — status, version, and knowledge-base counters

**Vector dimension mismatch.** If the configured embedding model's dimension does not match the existing vector index, `serve` clears the dataset DB and the startup reconcile re-enqueues all source files — the worker re-embeds them (clear-then-queue; there is no direct ingestion). `--auto-rebuild-vectors` performs this recovery automatically. See [Vector Rebuild](../concepts/vector-rebuild.mdx).

```bash
synopsis serve
synopsis --preset default serve --port 9090   # global preset, per-command flag after the subcommand
```

## `queue`

Inspect and repair the event task queue (`queue_tasks`). Both actions operate on the dataset-bound knowledge database and do not load the embedding model or the ONNX runtime; a non-empty dataset name is required (from the config or `--dataset`).

```
synopsis queue status [--source PATH] [--status NAME]
synopsis queue reset-retries [--source PATH] [--identity VALUE]
```

### `queue status`

Prints the queue as a table with the columns `type`, `identity`, `status`, `attempts`, `last_error`, `next_attempt_at`, followed by the task count. `type` is the event type (`doc:index`, `doc:delete`, `entity:link`); `identity` is the dedup key (a file path for `doc:*` events, a document id for `entity:link`).

| Flag | Description |
| --- | --- |
| `--source PATH` | Filter by source path prefix |
| `--status NAME` | Filter by exact status (`pending`, `processing`, `done`, `error`) |

### `queue reset-retries`

Re-queues failed tasks: status → `pending`, attempts → `0`, `next_attempt_at` → now. The background worker re-processes them on its next cycle. It applies to all event types.

| Flag | Description |
| --- | --- |
| `--source PATH` | Limit the reset to doc tasks of one source (path prefix) |
| `--identity VALUE` | Re-queue a single task (wins over `--source`); an error if no `error` task has that identity |

Without `--identity`, every `error` task (optionally narrowed by `--source`) is re-queued and the count is reported.

```bash
synopsis queue status
synopsis queue status --status error
synopsis queue reset-retries --identity workspace/datasets/edtech/content/documents/product/adaptive_learning_prd.md
```

## `db`

Dataset database maintenance. All three actions operate on the dataset-bound knowledge database and do not load the embedding model or the ONNX runtime; a non-empty dataset name is required.

```
synopsis db stats
synopsis db clear
synopsis db merge-entities <ID> --into <ID>
```

### `db stats`

Prints dataset statistics — documents, chunks, entities, entity links, facts, and queue-task counts. Read-only: no modification and no confirmation.

### `db clear`

Prints the same statistics, then asks for confirmation (`Confirm deletion? [y/N]` on stdin). Only `y` or `Y` deletes the entire dataset state directory `<workspace_dir>/datasets/<name>/state` — the knowledge DB **and** the vector index — from disk in one shot; any other answer aborts without modifying anything. The command closes the database connection before deleting the directory.

There is no standalone re-ingest subcommand: a full re-ingest is `db clear` followed by a `serve` restart, whose startup reconcile re-enqueues the source files and the worker re-embeds them, recreating the DB and the vector index.

### `db merge-entities`

Merges one entity into another: re-points facts (subject **and** object), chunk links, sources, and entity links, records **both names as aliases** of the survivor, and deletes the duplicate row — all in one transaction. This is the same merge primitive the within-domain cross-script linker action uses; see [Entity Resolution](../concepts/entity-resolution) for when it runs automatically.

```
synopsis db merge-entities <ID> --into <ID>
```

| Argument / flag | Description |
| --- | --- |
| `<ID>` (positional) | The entity id to merge away (the duplicate row, deleted after the merge) |
| `--into <ID>` | **required** — the surviving entity id |

Preconditions (checked **before any write**; a violation is a clear error and the database is left unmodified): both ids exist, the ids differ, and the two entities share the same `type` and `domain`.

After the preconditions pass, the command prints the dataset statistics block and asks `Confirm merge? [y/N]` on stdin. Only `y`/`Y` proceeds; any other answer (including EOF) aborts without modifying anything. On `y`, the merge summary is printed: the surviving and merged entity (name + id), the re-pointed row counts per table (`facts`, `facts dropped`, `chunk_entities`, `entity_sources`, `entity_links`), and the recorded aliases.

```bash
synopsis --dataset mydata db merge-entities 42 --into 17
```

Full walkthrough (finding the ids, sample output, and the alias-map alternative): [Entity Merging & Alias Maps](../guides/entity-merging.mdx).

```bash
synopsis db stats
synopsis db clear
synopsis db merge-entities 42 --into 17
```

## `model`

Manages embedding models against the model registry (`workspace/configs/onnx.yaml`); installed weights live under `workspace/models/`. Every action accepts an optional `NAME` positional argument.

```
synopsis model <list|download|delete|info|benchmark> [NAME]
```

| Subcommand | Argument | Description |
| --- | --- | --- |
| `model list` | — | List all registry models with version, vector dimension, and installation status |
| `model download [NAME]` | optional | Download and install a model; an omitted name uses the registry default |
| `model delete NAME` | **required** | Delete an installed model |
| `model info [NAME]` | optional | Show model details (description, version, dimension, source, install status); an omitted name uses the registry default |
| `model benchmark [NAME]` | optional | Benchmark embedding inference speed; an omitted name targets all installed models |

`model benchmark` prints a hardware header (CPU model, logical CPUs, total RAM, ONNX Runtime version) followed by the median/min/max embedding latency per model (warmup, then measured runs). The model must be installed first; with no name given and nothing installed the command exits `1` suggesting `model download`.

```bash
synopsis model list
synopsis model download bge-small-en-v1.5
synopsis model info bge-small-en-v1.5
synopsis model delete bge-small-en-v1.5
synopsis model benchmark               # all installed models
synopsis model benchmark bge-small-en-v1.5
```

## `onnx-runtime`

Manages the ONNX Runtime shared library that local embeddings run on. The library is downloaded on demand into `workspace/onnxruntime/` (version and per-platform URLs from `workspace/configs/onnx.yaml`).

```
synopsis onnx-runtime <install|status|uninstall>
```

| Subcommand | Description |
| --- | --- |
| `onnx-runtime install` | Install the ONNX Runtime library (a status line if already installed) |
| `onnx-runtime status` | Show version, installation status, library path, cache directory, and the supported platforms |
| `onnx-runtime uninstall` | Remove the installed library (it will be re-downloaded when needed) |

```bash
synopsis onnx-runtime install
synopsis onnx-runtime status
synopsis onnx-runtime uninstall
```

## `load-test`

Benchmarks all MCP tool handlers on generated data. Unless `--no-fill` is given, the command **clears and rewrites the target dataset** (all knowledge-base tables plus the vector index) with deterministic synthetic data, then runs the 12 tool cases directly (without HTTP).

```
synopsis load-test [--scale small|medium|large] [--seed N] [--iterations N] [--json PATH] [--no-fill]
```

| Flag | Default | Description |
| --- | --- | --- |
| `--scale` | `small` | Dataset scale: `small` (500 docs / 10k chunks / 2k entities / 5k facts), `medium` (5k / 100k / 20k / 10k), `large` (10k / 200k / 40k / 20k) |
| `--seed N` | `42` | PRNG seed for deterministic data generation |
| `--iterations N` | `100` | Measured iterations per tool case |
| `--json PATH` | — | Also write the report as JSON to `PATH` |
| `--no-fill` | `false` | Benchmark an existing database without generating data |

The report lists, per tool case: CALLS, AVG/P50/P95/P99/MAX ms, and QPS — human-readable on stdout, and the same report as JSON with `--json`. The local embedding model must already be downloaded (`synopsis model download [NAME]`).

:::warning
By default `load-test` **clears and rewrites the dataset**. Point `--config`/`--dataset` at a scratch dataset — never at a real one.
:::

Full guide: [Load Testing](../guides/load-testing.mdx) — phases, scales, report format, sample output, and interpretation.

## Exit codes

| Outcome | Exit code |
| --- | --- |
| Success (including `--version`, an aborted `db clear`, and an aborted `db merge-entities`) | `0` |
| Usage error: no subcommand, unknown subcommand, or invalid flags | `1` |
| Config load / validation failure | `1` |
| Database open / migration failure (incl. unrecovered dimension mismatch) | `1` |
| Model / ONNX runtime command error | `1` |

Every fatal error exits with code `1`.
