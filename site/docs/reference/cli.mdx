# CLI Reference

The `synopsis` binary uses **subcommand dispatch**. Global flags must appear **before** the subcommand; each subcommand then has its own flags.

```
synopsis [--config PATH] [--preset NAME] [--db PATH] [--version] <command> [command flags]
```

| Command | Purpose |
|---|---|
| `sync` | Force a full re-index of all sources and exit |
| `serve` | Start the MCP server (initial sync + file watching + optional scheduler) |
| `model` | Manage embedding models (`list`, `download`, `delete`, `info`, `benchmark`) |
| `onnx-runtime` | Manage the bundled ONNX Runtime library (`install`, `status`, `uninstall`) |
| `load-test` | Fill the database with deterministic synthetic data and benchmark all MCP tool handlers (14 cases) |

Running the binary with no subcommand (or with an unknown subcommand) prints usage on stderr and exits with code `1`.

## Global flags

| Flag | Description |
|---|---|
| `--config PATH` | Path to the configuration file, used verbatim (skips auto-search) |
| `--preset NAME` | Configuration preset name; the binary searches for `config.{NAME}.yaml` (default: `default`) |
| `--db PATH` | Path to the SQLite database file; overrides `database.path` from the config |
| `--version` | Print `synopsis <version>` and exit `0` |

```bash
# Use an explicit config and point at a scratch database
./bin/synopsis --config configs/config.default.yaml --db /tmp/scratch.db sync

# A custom preset
cp configs/config.default.yaml configs/config.prod.yaml
./bin/synopsis --preset prod serve
```

> **Note:** global flags use Go's standard `flag` parsing, which stops at the first non-flag argument. `synopsis serve --port 9090` works (subcommand flag), but `synopsis --port 9090 serve` fails (`--port` is not a global flag).

## Config path resolution

When `--config` is not given, the effective path is `config.{preset}.yaml` (default preset: `default`), searched in this exact order:

1. `<executable dir>/configs/config.{preset}.yaml`
2. `<executable dir>/config.{preset}.yaml`
3. `<parent of executable dir>/config.{preset}.yaml`
4. `<parent of executable dir>/configs/config.{preset}.yaml`
5. `<CWD>/configs/config.{preset}.yaml`
6. `<CWD>/config.{preset}.yaml`

If none of these exist, the binary falls back to `configs/config.{preset}.yaml` and fails with a config load error. The executable path is resolved through symlinks before the search.

## `sync`

Forces a full re-index of all configured sources and exits. This is the batch mode — no server, no watcher.

```
synopsis sync [--rebuild] [--auto-rebuild-vectors]
```

| Flag | Default | Description |
|---|---|---|
| `--rebuild` | `false` | Clear all existing data before re-indexing |
| `--auto-rebuild-vectors` | `false` | Automatically rebuild vectors on an embedding dimension mismatch |

Behavior:

- Loads and validates the configuration, discovers domains from `paths.global_config_path`, opens the database, and applies pending migrations.
- In `mode: local` embedding, the configured model is **downloaded automatically on first use** (stored under `<paths.data_dir>/models/`).
- A full source scan runs, then a summary is printed to **stderr**:

  ```
  === Sync Summary ===
  Sources processed: 4
  Documents created:  12
  Documents updated:  3
  Documents skipped:  9
  Errors:            1
  Duration:          12s
  ==========================
  ```

**Vector dimension mismatch.** If the configured `vector_dim` does not match the existing database, the command fails unless `--auto-rebuild-vectors` is passed (or `embeddings.auto_rebuild_vectors` is set in the config). In `--rebuild` mode the mismatch is skipped — the full reset discards the stale vectors anyway. See [Troubleshooting — Embedding dimension mismatch](../guides/troubleshooting.mdx#embedding-dimension-mismatch).

```bash
# Full re-index from scratch
./bin/synopsis sync --rebuild

# Incremental-style full scan (re-ingests only what changed; nothing is deleted)
./bin/synopsis sync
```

## `serve`

Starts the production mode: an optional initial full sync, the MCP server over HTTP/SSE, a file watcher for incremental re-indexing, and the background job scheduler.

```
synopsis serve [--no-initial-sync] [--port N] [--auto-rebuild-vectors]
```

| Flag | Default | Description |
|---|---|---|
| `--no-initial-sync` | `false` | Skip the full source scan on startup |
| `--port N` | `0` (use `server.port`) | HTTP listen port; overrides `server.port` from the config |
| `--auto-rebuild-vectors` | `false` | Automatically rebuild vectors on an embedding dimension mismatch |

Startup sequence:

1. Load configuration, discover domains, migrate the database, ensure the embedding model, open the cache database.
2. Resolve any vector dimension mismatch (see `sync` above).
3. Run a startup health check (database ping, document count, embedding provider).
4. Run the initial sync if `auto_update.initial_sync` is `true` and `--no-initial-sync` was not passed.
5. Start the job scheduler if `scheduler.jobs.orphan_cleanup.enabled` is `true`.
6. Load the in-memory knowledge graph (when `graph.enable_graph` and `graph.load_on_startup`), create the searcher, and start the MCP server on `server.host:server.port` (default `0.0.0.0:8080`) with endpoints `GET /sse`, `POST /message`, `GET /health` — see [MCP Tools](./mcp-tools/index.mdx).
7. Start the file watcher if `auto_update.enabled` and `auto_update.watch_sources` are both `true`; changed source files are re-indexed (debounced by `auto_update.debounce_seconds`).

Shutdown is graceful: the process stops cleanly on `SIGINT`/`SIGTERM` (sessions closed, HTTP server drained, scheduler stopped, 10-second timeout).

## `model`

Manages embedding models against the registry in the ONNX configuration file (`paths.onnx_config`, default `configs/onnx.yaml`).

```
synopsis model <list|download|delete|info|benchmark> [name]
```

| Subcommand | Argument | Description |
|---|---|---|
| `model list` | — | List all registry models with version, vector dimension, and installation status |
| `model download [name]` | optional | Download a model into `<data_dir>/models/<name>/`; omitted name uses the registry default (`models.default` in the ONNX config, e.g. `bge-small-en-v1.5`) |
| `model delete <name>` | **required** | Delete an installed model |
| `model info [name]` | optional | Show model details (description, version, dimension, source, files, install status/date); omitted name uses the registry default |
| `model benchmark [name]` | optional | Benchmark embedding inference speed for an installed model; omitted name targets **all** installed models |

```bash
./bin/synopsis model list
./bin/synopsis model download bge-small-en-v1.5
./bin/synopsis model info bge-small-en-v1.5
./bin/synopsis model delete bge-small-en-v1.5
./bin/synopsis model benchmark               # all installed models
./bin/synopsis model benchmark bge-small-en-v1.5
```

`model benchmark` prints a hardware header (CPU model, logical CPUs, total RAM, ONNX Runtime version) followed by per-model latency:

- **production** — the full provider path used during ingestion and search: tokenization plus padding to `seq=512`, then ONNX inference.
- **natural seq=N** for N = 32 / 128 / 512 — direct ONNX session on a sequence of that real length, without padding (isolates pure inference cost).

Each figure is the median of 9 runs after 3 warmup iterations (`batch=1`). The model must be installed first; with no name given and nothing installed the command exits `1` suggesting `model download`. Sample output:

```
Embedding Benchmark
----------------------------------------------------------------------
Hardware: 11th Gen Intel(R) Core(TM) i7-11800H @ 2.30GHz, 16 logical CPUs, ~31.07 GiB RAM
ONNX Runtime: 1.28.0

BGE Small English v1.5 (dim=384)
  production (padded to seq=512): median 87.9 ms/text [min 67.0, max 94.8], 9 runs
  natural seq=32  : median 6.2 ms/text [min 5.3, max 6.4], 9 runs (5186 tok/s)
```

Failing to load the config, the ONNX config, or a registry lookup exits with code `1`.

## `onnx-runtime`

Manages the ONNX Runtime library that `mode: local` embeddings run on. The library is downloaded on demand into `<data_dir>/` and cached there; version and per-platform download URLs come from the ONNX config file.

```
synopsis onnx-runtime <install|status|uninstall>
```

| Subcommand | Description |
|---|---|
| `onnx-runtime install` | Install the ONNX Runtime library (no-op with a status line if already installed) |
| `onnx-runtime status` | Show version, installation status, library path, cache directory, and the supported platforms from the ONNX config |
| `onnx-runtime uninstall` | Remove the installed library (it will be re-downloaded when needed) |

```bash
./bin/synopsis onnx-runtime install
./bin/synopsis onnx-runtime status
./bin/synopsis onnx-runtime uninstall
```

An unknown subcommand prints the subcommand usage and exits with code `1`.

## `load-test`

Populates the target database with deterministic synthetic data — written straight into the tables with real embeddings, bypassing the ingestion pipeline — then benchmarks all MCP tool handlers directly, without HTTP.

```
synopsis load-test [--scale small|medium|large] [--seed N] [--iterations N] [--json PATH] [--no-fill]
```

| Flag | Default | Description |
|---|---|---|
| `--scale` | `small` | Dataset scale: `small` (500 docs / 10k chunks / 2k entities / 5k facts), `medium` (5k / 100k / 20k / 10k), `large` (10k / 200k / 40k / 20k) |
| `--seed N` | `42` | PRNG seed for deterministic data generation |
| `--iterations N` | `100` | Measured iterations per tool case |
| `--json PATH` | — | Also write the report as indented JSON to `PATH` |
| `--no-fill` | `false` | Benchmark an existing database without generating data |

:::warning
By default `load-test` **clears and rewrites the knowledge base** (all knowledge-base tables plus `chunks_vec`). Point `--db` at a throwaway path — e.g. `--db /tmp/loadtest.db` — never at a production database. The local embedding model must already be downloaded (`synopsis model download <name>`); the command fails with a clear error instead of downloading it mid-run.
:::

Full guide: [Load Testing](../guides/load-testing.mdx) — phases, scales, report format, sample output, and interpretation.

## Exit codes

| Outcome | Exit code |
|---|---|
| Success (including `--version`) | `0` |
| Config load/validation failure | `1` |
| Domain discovery failure (missing or invalid ontology) | `1` |
| Database open / migration failure (incl. unrecovered dimension mismatch) | `1` |
| No subcommand, unknown subcommand, or invalid flags | `1` |
| Model / ONNX runtime command error | `1` |

Operational logs always go to the log output configured under `logging` (default: stderr).
