# The Pipeline

Synopsis is designed as one stage in an information pipeline — not a standalone assistant and not a full search platform. It takes **clean, normalized data in**, processes it into a structured, queryable knowledge base, and hands it back out as **MCP tools** that AI agents call.

```
┌─────────────────────────────────────────────────────────────────────┐
│  INPUT: cleaned data, normalized to a unified format                │
│  (.md, .json, .html) — sources tagged with domains                  │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│  PROCESSING (sync):                                                 │
│  parse → chunk → embed → NER → entities → facts                     │
│  → knowledge graph + hybrid search index                            │
│  → cross-domain linking (post step)                                 │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│  OUTPUT: MCP server (HTTP/SSE)                                      │
│  12 tools exposing chunks, entities, facts, and graph neighbors     │
│  with full provenance — consumed by AI agents                       │
└─────────────────────────────────────────────────────────────────────┘
```

Everything in this documentation follows this shape: **input → processing → MCP access**.

## Input

Synopsis ingests documents that are **already cleaned and normalized**. Supported formats:

| Format | File extensions       | Notes                                   |
| ------ | --------------------- | --------------------------------------- |
| Markdown | `.md`              | Section structure and metadata preserved |
| JSON     | `.json`            | Text fields extracted from objects/arrays |
| MediaWiki | `.json`           | Markup converted to clean JSON           |
| Web pages | `.html`           | HTML stripped, semantic structure kept   |

Where documents come from and which domains they belong to is configured as **sources** — each source is a path with a parser type and a list of domains (for example, an HR policy folder tagged `hr`, an internal wiki tagged `product` + `hr` + `it`).

Synopsis does **not** clean, deduplicate, or transform raw data. If your data arrives messy, that is a stage you run before Synopsis.

## Processing

The `sync` subcommand (`make sync`) runs the full ingestion pipeline inside a single SQLite database (`data/knowledge.db`). Stages, in order:

| # | Stage | What happens |
|---|-------|--------------|
| 1 | **Parse** | A format-specific parser turns each file into a structured document (Markdown, JSON, MediaWiki, web page, or unstructured). |
| 2 | **Chunk** | Documents are split into searchable fragments — header-based, fixed-size, or hybrid chunking, depending on the source. |
| 3 | **Embed** | Every chunk gets a vector from the local embedding model (ONNX Runtime). Vectors go into the `chunks_vec` table (sqlite-vec). |
| 4 | **NER** | Named entities are extracted per configured method (regex rules from the ontologies, offline statistical NER, or LLM-based extraction). |
| 5 | **Entities** | Extracted entities are deduplicated and resolved into canonical entity records, each tagged with its domain and confidence. |
| 6 | **Facts** | Structured subject → predicate → object facts are built from the extracted data, with confidence scores and links back to their source chunks and quotes. |
| 7 | **Graph + index** | Entities and facts form the knowledge graph; chunks feed the full-text index (SQLite FTS5, kept in sync automatically). |

After all sources are ingested, two post steps run in the same sync pass:

- **Orphan cleanup** — entities, facts, vectors, and documents that no longer point at live data are removed.
- **Cross-domain linking** — entities that appear in more than one domain are linked where applicable. See [Cross-Domain Linking](./cross-domain-linking.mdx).

Ingestion is **incremental**: unchanged documents are skipped by content hash, changed documents are refreshed. `make rebuild` (or `sync --rebuild`) wipes and re-ingests from scratch.

## Output

The `serve` subcommand (`make run`) starts the MCP server. It loads the knowledge graph into memory and exposes **12 tools** over HTTP/SSE (`/sse`, `/message`, plus `/health` for monitoring):

| Tool | Purpose |
|------|---------|
| `search` | Hybrid search (lexical + semantic, RRF-fused) over the whole knowledge base |
| `catalog_overview` | Aggregate statistics: documents, chunks, entities, facts, graph size |
| `catalog_documents` | List documents with pagination and filters (domain, type, name) |
| `catalog_entities` | List entities with pagination and filters (type, domain, name) |
| `search_entities_by_type` | All entities of a given type, paginated |
| `search_facts` | Search facts by predicate, entity name, status, domain |
| `get_document_context` | A full document: metadata, chunks with offsets, entities, fact IDs |
| `get_chunk_by_id` | A single chunk with document metadata and associated entities |
| `get_fact_by_id` | A single fact with subject/object details and source quotes |
| `get_entity_dossier` | A complete entity dossier: facts, sources, related entities, cross-domain links |
| `get_entity_relations` | BFS traversal of the knowledge graph from an entity |
| `get_entity_links` | Cross-domain links for an entity, with method, confidence, evidence |

The connected agent (Claude, Cursor, any MCP client) does the reasoning — Synopsis answers with structured data and provenance.

## What Synopsis deliberately does not do

- **It is not a full GraphRAG/KnowledgeRAG platform.** One job, done well: normalized documents in → queryable structured knowledge base out, with zero infrastructure.
- **It is not an ETL or data-cleaning stage.** Input is assumed clean and unified; prepare documents upstream.
- **It is not a chatbot or reasoning engine.** It exposes tools; the agent on the other side of MCP decides what to do with them.
- **It does not run external services.** One Go binary, one SQLite file, embeddings computed locally.
- **Fact review is not a feature yet.** Facts carry a status, and only `approved` facts surface in search expansion and dossiers, but a review workflow/UI is not implemented — it is tracked as roadmap.
