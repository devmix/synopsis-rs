# The Pipeline

Synopsis is one stage in an information pipeline — not a standalone assistant and not a full search platform. It takes **documents in** (Markdown, JSON, web pages), processes them into a structured, queryable knowledge base, and hands it back out as **MCP tools** that AI agents call.

```
┌─────────────────────────────────────────────────────────────────────┐
│  INPUT: documents (Markdown, JSON, web pages)                       │
│  configured as sources, each tagged with domains                    │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│  PROCESSING (background worker):                                    │
│  parse → chunk → embed (local ONNX) → NER → entities/facts         │
│  → cross-domain linking → knowledge graph + hybrid search index     │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│  OUTPUT: MCP server (Streamable HTTP /mcp + legacy HTTP+SSE)        │
│  12 read-only tools — chunks, entities, facts, graph neighborhoods  │
│  with full provenance — consumed by AI agents                       │
└─────────────────────────────────────────────────────────────────────┘
```

Everything in this documentation follows this shape: **input → processing → MCP access**.

## Input

Synopsis ingests documents in three source formats:

| Format    | Notes                                                        |
| --------- | ------------------------------------------------------------ |
| Markdown  | Section structure and heading breadcrumbs preserved          |
| JSON      | Text fields extracted from objects/arrays                    |
| Web pages | HTML stripped, semantic structure kept                       |

Where documents come from and which domains they belong to is configured as **sources** — each source is a directory with a parser type and a list of domains (for example, an HR policy folder tagged `hr`, an internal wiki tagged `product` + `hr` + `it`). When the parser type is not set explicitly, it is determined by a path heuristic (`wiki` → MediaWiki, `webpage` → web pages, otherwise unstructured). The source's domains are stamped into the documents' metadata.

## Processing

Each document goes through the stages below, in order, inside the background worker (see [How ingestion is triggered](#how-ingestion-is-triggered)):

| # | Stage | What happens |
|---|-------|--------------|
| 1 | **Parse** | A format-specific parser turns the file into a structured document (Markdown, JSON, or web page). |
| 2 | **Chunk** | The document is split into chunks. Each chunk stores `chunk_text` (the pure source slice, with byte offsets) and `search_text` (the body prefixed with the heading breadcrumb when present) — both search legs and the embedding model consume `search_text`. The chunk's own metadata bag (`section_title`, `heading_level`, `breadcrumb`, `image_paths`, …) is stored alongside it. |
| 3 | **Embed** | Every chunk is embedded by the local ONNX bge model, in batches of `batch_size` (default 100). A mismatch between the number of vectors and texts ends the document with an error. Vectors are written to the ANN index **after** the SQLite transaction commits — the chunk rows in the database are the source of truth. |
| 4 | **NER** | Named entities are extracted over the chunks by the configured providers — regex rules from the domain configs and LLM-based extraction with structured output — with the local models running on the ONNX runtime. |
| 5 | **Entities + facts** | Extracted entities are resolved into canonical records (deduplicated by name similarity, tagged with domain and confidence); structured subject → predicate → object facts are created with confidence scores, linked to their source chunks, and stored with a quote window around the entity's occurrence in the chunk. |
| 6 | **Write** | A single SQLite transaction writes the document, chunks, entity relations, and facts. A per-document error is counted in the run statistics and does not abort the run. |
| 7 | **Cross-domain linking** | After ingestion, entities that appear in more than one domain are linked where applicable (CEL expressions, equality, or LLM decisions). See [Cross-Domain Linking](./cross-domain-linking). |

**Deduplication by hash.** Each document is identified by its path; the SHA-256 of its content is compared with the stored hash. An unchanged document is skipped entirely; a changed one is refreshed — its old chunks, relations, and facts are deleted cascadingly, then the new data is written atomically in one transaction. Before indexing, a WAL snapshot of the database is written to the backups directory (a snapshot failure is a warning, not a failure).

**Pruning and cleanup.** When an indexed file vanishes from disk, its document and all its data are deleted cascadingly. Orphan cleanup removes entities without sources (infrastructure types excepted), facts without sources (approved ones excepted), and orphan documents; vectors without a live chunk are removed from the index.

## How ingestion is triggered

Synopsis keeps a single queue table — `document_jobs` — shared by the watcher, the startup scan, and the background worker:

- **Startup reconcile** — when `serve` starts, the dataset is scanned and the diff (new or changed files) is enqueued. (`--no-initial-sync` skips this step.)
- **File watcher** — while the server runs, file changes enqueue diffs into the same queue.
- **Background worker** — processes the queue with retries: a job that fails its maximum number of attempts lands in `error` status with `last_error` populated. Inspect the queue with `synopsis queue status` (filters: `--source PATH`, `--status NAME`); recover stuck jobs with `synopsis queue reset-retries` (moves `error` jobs back to `pending` with the attempt counter reset).

There is **no `sync` subcommand** — the queue *is* the ingestion model. A full re-ingest is `db clear` followed by a `serve` restart, after which the startup reconcile re-enqueues all files and the worker re-embeds them.

## Vectors

Embedding vectors live in a separate ANN index (usearch HNSW, disk-backed) that is **rebuilt from chunk text** — vector data is never carried over from a previous index, and the index dimensionality follows the embedding model from the configuration. The Vector Rebuild page covers the index mechanics in detail.

## Facts lifecycle

Facts carry a `status` — `draft`, `pending`, `approved`, or `rejected`. Only **`approved`** facts are exposed: they are the only facts that surface in search expansion, entity dossiers, and other read tools. A cross-domain fact (subject and object in different domains) is dropped with a warning at ingestion. Fact review is not a feature yet — the lifecycle is the data model, the review workflow is roadmap.

## Output

`synopsis serve` starts the MCP server. It exposes **12 read-only tools** over two transports — Streamable HTTP on `/mcp` (primary) and the legacy HTTP+SSE pair (`GET /sse` + `POST /message`) — plus `GET /health` for monitoring. See [MCP tools](../reference/mcp-tools) for the full list.

The connected agent (Claude, Cursor, any MCP client) does the reasoning — Synopsis answers with structured data and provenance.

## What Synopsis deliberately does not do

- **It is not a full GraphRAG/KnowledgeRAG platform.** One job, done well: documents in → queryable structured knowledge base out, with zero infrastructure.
- **It is not a chatbot or reasoning engine.** It exposes tools; the agent on the other side of MCP decides what to do with them.
- **It does not run external services.** One Rust binary, one per-dataset SQLite database, embeddings computed locally — the only network calls are to the user-configured LLM endpoint (NER and entity linking).
- **It does not migrate old data.** The database is built from scratch on first run.
