# Knowledge Graph

Synopsis builds a knowledge graph out of what it extracts during ingestion: **entities** are the nodes, **facts** are the directed edges, and **cross-domain entity links** are special edges that cross domain boundaries. At serve time the whole graph is loaded into memory, so multi-hop questions answer in a single traversal instead of a chain of database joins.

## Building blocks

| Concept | What it is | Where it lives |
|---------|-----------|----------------|
| **Entity** | A named thing — a person, department, system, policy, product — with a type, a domain, a description, metadata, and confidence | `entities` table; graph node |
| **Fact** | A structured statement: `subject → predicate → object` (e.g. *Anna S. → works_in → Engineering*), with confidence, a review status, and links to its sources | `facts` table; directed graph edge |
| **Fact source** | The provenance of a fact: the exact chunk and quote it was extracted from | `fact_sources` table |
| **Entity link** | A connection between two entities in *different* domains that represent the same real-world thing, with method, confidence, and evidence | `entity_links` table; cross-domain graph edge |

### Provenance

Every fact can be traced back to where it came from. `get_fact_by_id` returns the fact with its subject and object entities **and the source document quotes**, so an agent can show its work. Because extraction is confidence-scored and facts carry a status, only **approved** facts are ever included in search result expansion or entity dossiers — unapproved facts stay in the database but stay out of the answers.

## The in-memory graph

When the MCP server starts (`serve`), it loads all entities, facts, and entity links from the database into an in-memory graph:

- **Adjacency lists** for outgoing and incoming edges — O(1) neighbor access during traversal.
- **Name index** — case-insensitive lookup, qualified by domain (`hr:anna s.` — that is why two same-named people in different domains do not collide).
- **Type index** — all entities of a given type, optionally filtered by domain.
- **Cross-domain edges** with an inverse index, so boundary crossings are checked in O(1).

The graph is **static while the server runs** — it is simply a snapshot of the database. When re-ingestion happens (sync, or the file watcher during serve), the graph is reloaded and search expansion picks up the new structure automatically (with `--rebuild` you get a clean one from scratch).

## BFS traversal

`get_entity_relations` traverses the graph with breadth-first search from a start entity:

| Option | Values |
|--------|--------|
| `depth` | 1–10 (default 2) |
| Direction | `outgoing`, `incoming`, or `both` (default `both`) |
| Relation filter | restrict traversal to specific relation types |
| Node limit | hard cap of 1000 nodes keeps a traversal bounded |
| Cycle safety | visited-set protection; deterministic result ordering |

Two boundary rules are worth knowing:

1. **Traversals do not cross domain boundaries by default.** A traversal from an `hr` entity stays in `hr`, no matter how the facts connect.
2. With `include_cross_domain: true`, the traversal may step into another domain — **but only across an existing entity link** between the current node and its neighbor. Ordinary fact edges never carry a traversal across domains.

See [Cross-Domain Linking](./cross-domain-linking.mdx) for how those boundary-crossing links are created.

## Entity dossiers

`get_entity_dossier` is the one-call answer to "tell me everything you know about X". Given an entity ID or name (optionally disambiguated by domain), it returns:

- all **approved facts** for the entity (subject, predicate, object, confidence),
- the **source documents** it appears in,
- **related entities** via BFS traversal (depth 1–5, default 2),
- **cross-domain links** with full provenance (method, confidence, evidence).

That combination — facts, sources, neighborhood, and links in a single response — is what lets an agent resolve a multi-hop question ("who owns the policy that system X depends on?") with a couple of tool calls instead of a crawl.

## Graph-related MCP tools

| Tool | What it returns |
|------|-----------------|
| `get_entity_relations` | Nodes and edges found by BFS from an entity, up to the requested depth |
| `get_entity_dossier` | Complete dossier: facts, sources, related entities, cross-domain links |
| `get_entity_links` | Cross-domain links for an entity, each with method, confidence, and evidence |
| `get_fact_by_id` | A fact with subject/object entity details and source quotes |

Entity cataloging (`catalog_entities`, `search_entities_by_type`) and fact querying (`search_facts`) round out the surface — all 12 tools are listed in [The Pipeline](./pipeline.mdx#output).
