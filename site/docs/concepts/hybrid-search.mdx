# Hybrid Search

The `search` tool runs two independent retrievers — a **lexical** leg (SQLite FTS5, BM25) and a **semantic** leg (usearch HNSW vector similarity) — fuses their ranked lists with Reciprocal Rank Fusion, then post-processes the fused pool before returning results. Keyword precision and semantic recall reinforce each other: a chunk that both retrievers find rises to the top.

```
                  ┌──────────────────────────────────────┐
    query ────────┤ both legs run in parallel (tokio)    │
                  └──────────────┬───────────────────────┘
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
   Lexical: SQLite FTS5 (chunks_fts)        Semantic: usearch HNSW index
   BM25 over search_text                    kNN over search_text embeddings
         │                                               │
         └───────────────────────┬───────────────────────┘
                                 ▼
                  Reciprocal Rank Fusion (k = 20)
                  final = 0.7 · rrf + 0.3 · bm25
                                 ▼
         enrich → rerank → truncate to top_k → graph expansion
```

A domain filter passed to `search` is applied **inside each sub-search** — at the SQL level for the lexical leg, on the application side (with ×3 over-fetching) for the semantic leg — before fusion and truncation, so up to `top_k` results within the requested domain survive. Domain comparison is normalized (case/whitespace).

## The two retrievers

| | Lexical | Semantic |
|---|---------|----------|
| Index | SQLite **FTS5** virtual table `chunks_fts`, built over `search_text` and kept in sync with chunk writes via triggers | **usearch** HNSW index — disk-backed (mmap), scalar-quantized (bf16 default), L2 metric; two-layer RAM/DISK persistence with per-segment WAL |
| Matching | **BM25** over `search_text` — the chunk body prefixed with its heading breadcrumb, so a query term in a heading matches its sections | The query is embedded by the local ONNX bge model; kNN returns the nearest `(chunk_id, distance)` pairs |
| Query handling | FTS5 syntax: terms, phrases, prefix matching | The index is disk-backed and quantized; the query path never loads the embedding model into the index itself |
| Strong at | Exact terminology: names, codes, IDs, policy titles | Paraphrase: "how much do I get paid when away" matching "vacation salary" |

Both sub-searches are independent: if one fails, the other's results are still returned; an error is propagated only if **both** fail (mentioning both reasons). An empty query returns an empty result. The final post-search pipeline (enrich → rerank → truncate → expand) runs on all paths — including when only one leg is used.

## Fusion: Reciprocal Rank Fusion

Fused scores are computed with **Reciprocal Rank Fusion (RRF)**, k = 20:

```
rrf(chunk)   = Σ over lists  1 / (k + rank(chunk in list))     # k = 20, ranks are 1-based
final(chunk) = 0.7 · rrf_norm(chunk) + 0.3 · bm25_norm(chunk)
```

- Each retriever contributes a per-chunk term `1 / (k + rank)`; **chunks that appear in both lists accumulate both terms**, so agreement between the retrievers naturally lifts them.
- BM25 scores are min-max normalized to [0, 1] **over the lexical list's entries only**; chunks that only the semantic leg found get a neutral 0.5, so neither side is favored. RRF scores are normalized into [0, 1] before the blend.
- The final score is the weighted blend above: **0.7 to the fused rank signal, 0.3 to the calibrated BM25 signal**.
- Results are sorted by descending final score, with chunk ID as a deterministic tiebreak (the smaller `chunk_id` ranks higher on a tie), and trimmed to the fusion pool size.
- Every result is labeled with its origin: `lexical`, `semantic`, or `hybrid` (found by both).

RRF was chosen over a weighted score combination on purpose: BM25 and L2 distance live on unrelated scales, so RRF needs no calibration — one parameter (k) instead of a bag of weights, and items found by both strategies win.

## Post-search pipeline

After fusion, the pool goes through four steps:

1. **Enrich** — each chunk is annotated, in batched lookups (no N+1), with the document path, the merged document type, the owning document's `updated_at` (RFC 3339), the reranker flags (`is_deprecated`, `is_official`, `valid_to`) from the document metadata, the domain list, and the entities associated with the chunk.
2. **Rerank** — business rules rescale scores and re-sort:

   | Rule | Multiplier | Applied when |
   |------|------------|--------------|
   | Deprecated content | × 0.2 | the document is marked deprecated |
   | Official policy | × 1.5 | the document is marked official |
   | Expired document | × 0.1 | its `valid_to` date is in the past |
   | Freshness boost | × 1.2 (default) | the document was updated within the last 90 days (default) |
   | Authority boost | per document type | from the configuration map (e.g. `policy: 1.5`) |

   The multipliers **compose** (a deprecated *and* official document is × 0.2 × 1.5). After the boosts, the list is re-sorted by descending score and the ranks are re-numbered. The defaults are 0.2 / 1.5 / 1.2 / 90; configuration overrides only positive values.
3. **Truncate** — the reranked list is cut to the requested `top_k`. Truncation happens *after* reranking so the best-adjusted results survive.
4. **Graph expansion** — if enabled, each entity in the surviving results is expanded by breadth-first search over the knowledge graph (both directions, bounded by `max_depth`/`max_nodes`); **approved** facts are loaded in batches and the edges and facts are attached as `related_entities` metadata. Expansion is best-effort: if it fails, results are still returned without the graph context. See [Knowledge Graph](./knowledge-graph).

## What a result carries

- **`text` is the chunk's pure body** — the `chunk_text` byte-offset slice. The section context (breadcrumb, section title) is not glued into the text; it travels as structured data.
- **`metadata`** — the chunk's own metadata bag: `section_title`, `heading_level`, `breadcrumb`, `image_paths`, and any other chunk-specific keys the chunker computed (an empty bag is omitted).
- **`updated_at`** — the owning document's freshness timestamp in RFC 3339 (omitted when the document has no parseable timestamp), so a RAG client can see hit freshness without a second `get_document_context` call.
- **Provenance** — document path, type, domains, rank, and the entities the chunk mentions: everything the agent needs to cite and follow up with `get_document_context`, `get_entity_dossier`, or `get_entity_relations`.

## Why it matters for your agent

- A `search` result is a **chunk, not a score** — with provenance, the metadata bag, and freshness.
- `related_entities` means one search call already surfaces the neighborhood of what the agent found; deeper questions can be answered with `get_entity_relations` or `get_entity_dossier` instead of more full-text queries.
- The `domain` argument is the cheapest way to scope a question ("which **hr** document says…") — it runs inside both retrievers, not as a post-filter over a smaller pool.
