# Domains

A **domain** is a business area with its own vocabulary: HR has salaries and grades, IT has systems and servers, Product has customers and features. Synopsis is **domain-based by configuration** — each domain ships an XML ontology that defines which entity types exist there, how they relate, and how to extract them from text.

That gives you one service over a heterogeneous knowledge base: different domains can have completely different entity schemas, and everything still lands in the same graph and search index.

## What domains drive

- **Extraction.** Each domain's ontology lists entity types (with attributes and synonyms) and regex extraction rules; NER during ingestion uses them to decide what to extract from tagged sources.
- **Identity.** Every entity is tagged with the domain it was extracted in. Name lookups are domain-qualified (`domain:lowercase_name`) — `employee` in `hr` and `employee` in `it` do not collide, and two same-named entities in different domains are candidates for [cross-domain linking](./cross-domain-linking) instead of being merged blindly.
- **Search scoping.** `search`, catalogs, and entity queries accept a `domain` filter, applied inside the retrievers.
- **Graph boundaries.** Traversals stay within the start entity's domain unless you explicitly ask to follow entity links across domains — fact edges never cross.

## Ontology files

Domain configuration lives in **XML, not YAML** — in the dataset's ontology directory:

```
workspace/datasets/<dataset>/ontology/
├── global.xml                 ← the global pool + pipeline configuration
└── domains/
    ├── domain_hr.xml          ← HR domain
    ├── domain_it.xml          ← IT domain
    └── domain_product.xml     ← Product domain
```

Ingestion sources are declared in `global.xml` + `domains/*.xml` (not in the YAML preset).

### Discovery and resolution at startup

On startup, the domain registry:

1. loads and validates **`global.xml`** — the *global pool*: entity and relation definitions shared by every domain, plus the pipeline-wide configuration (cross-domain linking, NER methods, sources);
2. scans **`domains/*.xml`** — every matching file becomes a domain;
3. resolves each domain's **effective schema as two layers** — lookup searches the **domain layer first, then the global pool** (shadowing). A domain definition with an ID matching a global one **overrides the global one for this domain** — the global version remains available for the other domains, and no warning is emitted;
4. validates references **on the merged layers** — relation → entity references and ref attributes resolve against both layers together, so a global relation referencing an entity overridden by a domain resolves to the domain version.

### Validation at load time

Configuration errors surface immediately rather than silently degrading ingestion:

| Problem | Behavior |
|---------|----------|
| A domain file is missing | **startup error** |
| A domain XML is syntactically invalid | **startup error** (the message names the ontology file) |
| A regex extraction pattern does not compile | **startup error** (patterns are compiled at load time; the message names the file and the rule) |
| `global.xml` is missing | **not an error** — the global pool is simply empty |

### Anatomy of a domain file

```xml
<domain name="hr" version="1.0.0" description="HR policies, employee data, organizational structure">

    <entities>
        <entity id="salary" name="Salary" description="Compensation element">
            <attributes>
                <attribute name="title" type="string" required="true"/>
                <attribute name="amount" type="number"/>
                <attribute name="currency" type="string"/>
            </attributes>
            <synonyms>
                <synonym>compensation</synonym>
                <synonym>bonus</synonym>
            </synonyms>
        </entity>
    </entities>

    <relations>
        <relation source="grade" predicate="salary_of" target="salary"
                  description="Salary level for an employee grade">
            <attributes>
                <attribute name="amount" type="number"/>
            </attributes>
        </relation>
    </relations>

    <extraction>
        <regex-rules>
            <regex id="employee_id" entity="employee" pattern="EMP-\d{4,6}" confidence="0.95"/>
        </regex-rules>
    </extraction>

    <confidence auto_publish_threshold="0.7" review_threshold="0.6" reject_threshold="0.4"/>
</domain>
```

| Element | Purpose |
|---------|---------|
| `<domain>` | Name (used everywhere — source tags, filters, lookups), version, description |
| `<entities><entity>` | An entity type: `id`, `name`, `description`, with `<attributes>` (`name`, `type`, `required`, `target`) and `<synonyms>` used for extraction and normalization |
| `<relations><relation>` | A relation type between two entity types: `source → predicate → target`, with optional `<attributes>` |
| `<extraction><regex-rules><regex>` | Regex rules for extracting an entity type, each with its own `confidence` |
| `<confidence>` | Per-domain thresholds applied during entity extraction: `auto_publish_threshold`, `review_threshold`, `reject_threshold` |

Note the **plural wrappers** (`<entities>`, `<relations>`, `<regex-rules>`): every group of repeating elements is wrapped. This is the deliberate breaking format change of 2026-08-19 — compatibility is by semantics, not by the old flat layout.

### The global pool

`global.xml` defines what every domain shares. Its blocks, in the same wrapped format:

| Block | Contents |
|-------|----------|
| `<entities>` | `<entity id= name= description=>` with `<attributes>` and `<synonyms>` — entity types available in every domain |
| `<relations>` | `<relation source= predicate= target= description=>` with `<attributes>` — relation types available in every domain |
| `<extraction>` | `<regex-rules><regex id= entity= pattern= confidence=>` — shared regex extraction rules |
| `<sources>` | `<source path= type= disabled= space= dataset=>` with `<domains><domain>` — the ingestion sources and the domains each one is tagged with |
| `<cross-domain-links>` | `<methods><method>`, `<equals><min-words>`, `<llm-confidence-threshold>`, `<batch-size>`, and `<expressions><expression>` (each with `<name>`, `<description>`, `<priority>`, `<where>`, `<relation-type>`) — the [cross-domain linking](./cross-domain-linking) configuration |
| `<ner>` | `<methods><method>` — the NER methods used during ingestion |

### The demo dataset

The tracked `edtech` demo dataset ships three domains over the global pool:

| Domain | Own entity types (beyond the pool) | Example relations |
|--------|------------------------------------|-------------------|
| **hr** | `salary`, `grade` | `salary_of` |
| **it** | `system`, `service`, `server`, `database`, `network_component` | `runs_on`, `uses_database`, `provides`, `consumes`, `hosted_on`, `depends_on`, `replicates_to` |
| **product** | `product`, `feature`, `customer`, `competitor`, `market_segment` | `has_feature`, `purchased_by`, `competes_with`, `targets_segment`, `belongs_to_competitor` |

The global pool adds `employee`, `department`, `policy`, `role`, and `email` (with relations `works_in`, `owns_policy`, `has_role`, `belongs_to`, `manages`, `has_email`) and a shared email regex rule (confidence 0.95). Because the pool is layered in, every domain also has those types — which is exactly what makes cross-domain linking meaningful: the same system can appear as an entity in `hr`, `it`, and `product` at once.

## Adding a new domain

1. Create `workspace/datasets/<dataset>/ontology/domains/domain_<name>.xml` with a `<domain name="<name>" …>` root and its entities, relations, extraction rules, and confidence thresholds.
2. Restart the server — discovery and validation run at startup, and a malformed file fails startup with a message that names it.
3. Tag your sources with the domain in the `<sources>` block of `global.xml` so ingested documents and entities get it.
