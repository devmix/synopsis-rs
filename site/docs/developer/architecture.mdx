# Architecture

This page explains how the Synopsis binary is built: the 11-crate Rust workspace, the dependency graph fixed between the crates, the data flow from ingestion to search, the storage layout, and the four design decisions (ADRs 0001–0004) behind them.

The user-facing story — what goes in, what comes out — is [The Pipeline](../concepts/pipeline). This page is about the code that makes it happen.

## Workspace crates

The project is a Cargo workspace with 11 crates:

| Crate | Role |
|---|---|
| `crates/config` | YAML presets, onnx.yaml download config, XML ontologies |
| `crates/db` | rusqlite connections, migrations, DAOs, FTS5 queries |
| `crates/vectors` | ANN index contract (trait) + usearch engine; WAL + compaction |
| `crates/embedding` | ONNX runtime lifecycle + bge-m3 int8 provider |
| `crates/ingestion` | document parsers, chunkers, NER, entity extraction, event task queue + worker |
| `crates/graph` | knowledge graph (petgraph) + CEL linkers + minijinja prompts |
| `crates/search` | hybrid (FTS5 + vector) search with RRF fusion |
| `crates/mcp` | MCP server (double transport) + 12 tool handlers |
| `crates/llm` | OpenAI-compatible LLM client (NER + entity linking); base tier, depends only on `config` |
| `crates/utils` | shared helpers (temporal: RFC 3339 UTC); leaf crate any crate may depend on |
| `crates/cli` | the `synopsis` binary: subcommand dispatch, flags, config resolution |

The layering is deliberate: `config`, `db`, `vectors`, `utils`, and `llm` form the base tier; `embedding`, `ingestion`, and `graph` build on it; `search` composes the three; `mcp` exposes the result; `cli` assembles the binary. `cli` is also the only crate that logs (tracing) — the library crates stay logger-less.

## Dependency graph

The dependency graph is fixed by design (D1) — a crate depends only on the tier below it:

```
  base tier      config · db · vectors · utils · llm
                          │
                          ▼
  middle tier    embedding · ingestion · graph
                          │
                          ▼
                   search ──▶ mcp ──▶ cli
```

## Data flow: ingestion → search

Documents (Markdown, JSON, web pages) move through the workspace in one direction:

```
  Documents (Markdown, JSON, web pages)
        │
        ▼
   ingestion    parse → chunk → embed (local ONNX) → NER → entity/fact extraction
                cross-domain linking; a background worker drains the queue_tasks event queue
        │
        ▼
  db / vectors / graph
    · per-dataset knowledge DB — documents, chunks + FTS5, entities, facts, links
    · usearch index files — disk-backed, scalar-quantized ANN (per dataset)
    · knowledge graph — petgraph index over entities and relations
        │
        ▼
  search       FTS5 (BM25) + vector (usearch HNSW) in parallel → RRF fusion → reranking
        │
        ▼
  mcp          12 read-only tools over Streamable HTTP (/mcp) + legacy HTTP+SSE (/sse, /message)
        │
        ▼
  cli          the synopsis binary: serve, queue, db, model, onnx-runtime, load-test
```

Query time: an MCP client calls `search`; the lexical and semantic legs run in parallel, are fused with RRF, reranked, and returned as JSON. If one leg fails, the other still returns results — only a double failure propagates as an error. Details: [Hybrid Search](../concepts/hybrid-search) and the [`search` tool](../reference/mcp-tools/search).

## Storage

All runtime state lives under `workspace/` (gitignored; created and downloaded by the binary). There are **two SQLite databases** plus the ANN index files:

- **Per-dataset knowledge DB** — `workspace/datasets/<name>/state/knowledge.db`: documents, chunks with the FTS5 index, entities, facts, entity links, and the `queue_tasks` event queue. It is always built from scratch: one squashed init migration, `PRAGMA user_version` as the sole source of schema state — the `_schema_migrations` table is deliberately not created, and existing `knowledge.db` files are never opened or upgraded.
- **Global cache DB** — `workspace/db/cache/cache.db`: the persistent LLM/NER decision caches, shared across datasets and independent of any single dataset.
- **usearch index files** — under the dataset's `state/`: the disk-backed, scalar-quantized HNSW index with its WAL and segments. Vectors are rebuilt from chunk text; they are never read from any previous store.

SQLite itself is compiled in-tree (rusqlite + bundled libsqlite3-sys): FTS5 ships with every build, there are no system dependencies, and a build cannot silently lack FTS5 support.

## Design decisions (ADRs 0001–0004)

The four architecture decisions are recorded as ADRs. Each is summarized here; the full text of each ADR is in the repository under `docs/adr/`, and the site-side summaries live in the *Architecture Decision Records* page of this section.

### ADR 0001 — SQLite/FTS5 seam (bundled, source-compiled)

Synopsis owns the full SQLite/FTS5 path in Rust: SQLite is compiled from source into the binary (rusqlite + libsqlite3-sys, `bundled`), so FTS5 ships with every build and the "no fts5 module → silently degrade" failure class is excluded by construction — no C-compiler flags anywhere, and the one-binary / no-external-dependencies contract holds across all five cross-build targets. The same ADR froze the migration mechanism: `rusqlite_migration` with the SQL embedded at compile time, a single squashed init migration, and `PRAGMA user_version` as the sole source of schema state — the `_schema_migrations` table is never created, and pre-existing `knowledge.db` files are never opened or upgraded.

### ADR 0002 — ONNX Runtime seam (ort, load-dynamic)

Embeddings and NER run locally through ONNX Runtime, which the binary loads dynamically: the runtime `.so`/`.dylib` is neither downloaded nor linked at build time — it is opened at runtime from a local path, and the runtime and model weights are downloaded on demand per the `onnx.yaml` registry (URL + size + SHA-256 verified). The bindings are pinned to `ort` 2.0.0-rc.13 (`load-dynamic`, default features off) — a deliberate pre-release pin whose API churn is isolated in `crates/embedding`. The spike also proved determinism: identical inputs produce bit-identical vectors across independent processes, which is what makes fixture-based parity testing possible.

### ADR 0003 — ANN engine (LanceDB; superseded by 0004)

The first ANN-engine decision froze LanceDB (IVF-HNSW with u8 scalar quantization) after spike measurements passed the laptop gates (p95 < 10 ms, recall@10 ≥ 0.95, RSS delta ≤ ~2 GB) at 250K scale. The full N=1M run then failed both the p95 and recall gates with no runtime setting able to meet them at once, and on 2026-08-31 the ADR was superseded: the lance engine was removed and usearch became the sole ANN engine (ADR 0004).

### ADR 0004 — usearch: two-tier RAM/DISK with per-segment WAL

The vector engine is usearch (2.x, C++11 HNSW core via cxx) arranged as a two-tier RAM/DISK architecture: a RAM segment (an in-memory copy, persisted by explicit saves) plus read-only DISK segments (mmap views that are never mutated), searched in parallel and merged with the freshest tier winning on duplicates. A per-segment WAL in SQLite records only invalidations, sidecar key manifests make key enumeration scan-free, RAM overflow flushes a new monotonically-numbered segment, and background compaction runs when the stale-vector threshold is exceeded — disk-backed and scalar-quantized (bf16 default), sized for the 16 GB laptop, with the query path never loading the embedding model.
