# CI/CD

Two workflows live in `.github/workflows/`: **`ci.yml`** runs on every push and pull request to `main`; **`release.yml`** cross-builds, packages, and publishes binaries when a `v*` tag is pushed.

Both target a **self-hosted Gitea runner**, and the workflows are Gitea-compatible *on purpose*: the runner has no artifact service, so the standard GitHub artifact/release actions abort, and nothing can be passed between jobs. The consequences:

- the dev CI stays fast — the 5-target cross-build lives in `release.yml` only;
- the release is a **single job** that builds, packages, and publishes on one runner;
- where an artifact action is needed (the coverage lcov file), the Gitea fork `ChristopherHX/gitea-upload-artifact` is used, and the release is published with the Gitea fork `akkuman/gitea-release-action`.

Do not "upgrade" these to the standard GitHub actions — they break on the Gitea runner.

## CI workflow (`ci.yml`)

Triggered on push and pull request to `main`, with `concurrency: cancel-in-progress` so a stale run is cancelled when a new commit lands. Two jobs run in parallel on `ubuntu-latest`:

| Job | Steps | Notes |
|---|---|---|
| **checks** | `cargo fmt --check` → `cargo clippy --all-targets -- -D warnings` → `cargo test` | one job runs all three gates sequentially — they share a single toolchain install and cargo cache; `cargo test` compiles and links the whole workspace, so it doubles as the native build check |
| **coverage** | `cargo llvm-cov --workspace --lcov --output-path lcov.info` (cargo-llvm-cov 0.9.0) → upload the lcov file as a run artifact | runs in parallel to `checks` (no `needs:`) — measure-first, no gates: a coverage failure must not block the core gate, and there is deliberately no `--fail-under-*` flag |

Setup steps for both jobs:

1. **Install the pinned toolchain** — `dtolnay/rust-toolchain@1.96.0` (components `clippy, rustfmt` for `checks`, `llvm-tools-preview` for `coverage`; the action installs with `--profile minimal`, so components must be requested explicitly).
2. **Cache cargo artifacts** — `Swatinem/rust-cache@v2` caches `~/.cargo` and `./target`, keyed by the installed rustc version, so it runs after the toolchain step.

### The toolchain-pin gotcha

`rust-toolchain.toml` pins channel **1.96.0**, and the `@<rev>` of the `dtolnay/rust-toolchain` action must **match that file exactly**: rustup resolves the directory override from the file, and a mismatching install makes **every cargo command fail** with "toolchain not installed". When the toolchain is bumped, the file and the action revision in both workflows change in the same commit.

## Release workflow (`release.yml`)

Triggered by **push of tags matching `v*`** (for example `v0.1.0`). A single job on `ubuntu-latest` does everything — the Gitea runner has no artifact service, so no work product can be passed between jobs:

1. Check out with full history (`fetch-depth: 0`) so the tag — and thus the version — is available.
2. Install the pinned toolchain with all five target stds up front (the job cross-compiles for each target in turn; no clippy/rustfmt components are needed).
3. `cargo install --locked cargo-zigbuild` — the binary lands in `CARGO_HOME`, which the rust-cache step already caches, so only a cold cache pays the compile.
4. Install **Zig 0.16.0** (`mlugg/setup-zig@v2`) — the C toolchain for every target.
5. **Build-and-package loop**: for each of the five targets — `cargo zigbuild --release --target <t>`, strip with `zig objcopy --strip-all` (one command handles all three object formats: ELF, PE/COFF, Mach-O), then rebuild a clean `stage/` directory and archive it as `dist/synopsis_<version>_<name>.<ext>`.
6. Write `SHA256SUMS.txt` over all archives.
7. Publish the **Gitea Release** via `akkuman/gitea-release-action@v1` — the body is deliberately empty (manual release), the name defaults to the tag, and a dash-suffixed tag (`vX.Y.Z-rc*`) is marked as a prerelease.

### The five targets

| Target triple | Platform | Archive (v0.1.0 example) |
|---|---|---|
| `x86_64-unknown-linux-musl` | Linux amd64 | `synopsis_0.1.0_linux_amd64.tar.gz` — **fully static** |
| `aarch64-unknown-linux-gnu` | Linux arm64 | `synopsis_0.1.0_linux_arm64_gnu.tar.gz` |
| `aarch64-unknown-linux-musl` | Linux arm64 | `synopsis_0.1.0_linux_arm64_musl.tar.gz` |
| `x86_64-pc-windows-gnu` | Windows amd64 | `synopsis_0.1.0_windows_amd64.zip` |
| `aarch64-apple-darwin` | macOS arm64 | `synopsis_0.1.0_darwin_arm64.tar.gz` |

**windows-gnu, not msvc** — Zig cannot link the MSVC ABI from a Linux host, so the Windows target uses the GNU ABI.

### What ships in an archive

Each archive bundles exactly:

- the stripped `synopsis` binary (`synopsis.exe` on Windows),
- the root `README.md` (it doubles as the end-user documentation shipped with the binary),
- `workspace/configs/**` (presets, `onnx.yaml`, prompt templates),
- `workspace/datasets/edtech/ontology/**` (the demo ontology).

Deliberately excluded: the ONNX runtime library and the model weights (gitignored runtime artifacts the binary downloads per `onnx.yaml`) and the demo corpus.

## Release flow

```
git tag -a v0.1.0 && git push origin v0.1.0
      │
      ▼
release.yml (single job): 5× zigbuild → strip → package → SHA256SUMS.txt
      │
      ▼
Gitea Release with the 5 archives + checksum file
```

- The build runs first and the publish second: if the cross-build fails, **nothing is published** — fix and re-push the same tag to retry.
- The 5-target build lives in `release.yml` and only there — the dev CI stays fast.
