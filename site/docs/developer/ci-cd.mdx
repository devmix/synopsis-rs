# CI/CD

Two workflows live in `.github/workflows/`: **`ci.yml`** runs on every push and pull request to `main`; **`release.yml`** cross-builds, packages, and publishes binaries when a `v*` tag is pushed.

Both run on GitHub's `ubuntu-latest` runners with the standard `actions/*` tooling.

## CI workflow (`ci.yml`)

Triggered on push and pull request to `main`, with `concurrency: cancel-in-progress` so a stale run is cancelled when a new commit lands. One job (`ci`) runs the four stages sequentially — they share a single toolchain install and cargo cache:

1. **Install the pinned toolchain** — `dtolnay/rust-toolchain@1.96.0` with components `clippy, rustfmt, llvm-tools-preview`.
2. **Cache cargo artifacts** — `Swatinem/rust-cache@v2` caches `~/.cargo` and `./target`, keyed by the installed rustc version (runs after the toolchain step), with `shared-key: host` so the dev CI and the release `gate` job share one cache slot.
3. **`cargo fmt --check`** → **`cargo clippy --all-targets -- -D warnings`** → **`cargo test`** — `cargo test` compiles and links the whole workspace, so it doubles as the native build check.
4. **Coverage** — `cargo llvm-cov --workspace --lcov --output-path lcov.info` (cargo-llvm-cov 0.9.0, installed via `taiki-e/install-action@v2`), run with `continue-on-error` and uploaded as an artifact via `actions/upload-artifact@v4`. Measure-first, no gates: a coverage failure must not block the core gate, and there is deliberately no `--fail-under-*` flag.

### The toolchain-pin gotcha

`rust-toolchain.toml` pins channel **1.96.0**, and the `@<rev>` of the `dtolnay/rust-toolchain` action must **match that file exactly**: rustup resolves the directory override from the file, and a mismatching install makes **every cargo command fail** with "toolchain not installed". When the toolchain is bumped, the file and the action revision in both workflows change in the same commit.

## Release workflow (`release.yml`)

Triggered by **push of tags matching `v*`** (for example `v0.1.0`). Three jobs run in sequence:

1. **`gate`** — `cargo fmt --check` → `cargo clippy --all-targets -- -D warnings` → `cargo test` on the tagged commit (toolchain 1.96.0, rust-cache `shared-key: host` — the same slot as dev CI).
2. **`build`** — a **5-way parallel matrix**, one leg per target triple. Each leg installs the pinned toolchain (only that target's std), caches under a **per-leg rust-cache key**, installs `cargo-zigbuild` (`--locked`) and **Zig 0.16.0** (`mlugg/setup-zig@v2`), then runs `cargo zigbuild --release --target <t>` and packages `synopsis_<version>_<name>.<ext>`. There is **no strip step** — `[profile.release] strip = true` strips at link time.
3. **`publish`** — `actions/download-artifact@v4` fetches all five archives, writes `SHA256SUMS.txt`, and creates the GitHub Release via **`softprops/action-gh-release@v3`** with a changelog categorized from conventional commits.

If any leg fails, **nothing is published** — delete the tag and re-push to retry.

### The five targets

| Target triple | Platform | Archive (v0.1.0 example) |
|---|---|---|
| `x86_64-unknown-linux-gnu` | Linux amd64 | `synopsis_0.1.0_linux_amd64.tar.gz` |
| `aarch64-unknown-linux-gnu` | Linux arm64 | `synopsis_0.1.0_linux_arm64.tar.gz` |
| `x86_64-pc-windows-gnu` | Windows amd64 | `synopsis_0.1.0_windows_amd64.zip` |
| `aarch64-apple-darwin` | macOS arm64 | `synopsis_0.1.0_darwin_arm64.tar.gz` |
| `x86_64-apple-darwin` | macOS amd64 | `synopsis_0.1.0_darwin_amd64.tar.gz` |

**windows-gnu, not msvc** — Zig 0.16 has no libc/headers for the MSVC target, so C code (ring, libsqlite3-sys, usearch) cannot compile for msvc from a Linux host; the Windows leg carries a one-line case-sensitivity shim for usearch's `#include <Windows.h>`.

### What ships in an archive

Each archive bundles exactly:

- the stripped `synopsis` binary (`synopsis.exe` on Windows) — stripped by `[profile.release] strip = true` at link time,
- the root `README.md` (it doubles as the end-user documentation shipped with the binary),
- `workspace/configs/**` (presets, `onnx.yaml`, prompt templates),
- `workspace/datasets/edtech/ontology/**` (the demo ontology).

Deliberately excluded: the ONNX runtime library and the model weights (gitignored runtime artifacts the binary downloads per `onnx.yaml`) and the demo corpus.

## Release flow

```
git tag -a v0.1.0 && git push origin v0.1.0
      │
      ▼
gate (fmt + clippy + test)
      │
      ▼
build: 5 legs in parallel — zigbuild → package
      │
      ▼
publish: SHA256SUMS.txt → GitHub Release with the 5 archives
```

- The 5-target build lives in `release.yml` and only there — the dev CI stays fast.
- The build runs before the publish: if a leg fails, **nothing is published** — fix and re-push the same tag to retry.
