# Testing

Synopsis is tested with the standard cargo toolchain: unit and integration tests co-located in each crate, differential parity tests against recorded fixtures, and — in CI — the full workspace suite on every push.

## Running the suite

```bash
cargo test                                # full workspace, ~20 s warm; no services or network needed
cargo test -p <crate>                     # a single crate
cargo test -p <crate> -- <TestNameFilter> # a single test (name filter after --)
```

The suite is hermetic: no network, no running services, no downloaded models. The embedding and LLM paths are exercised against local test doubles and the cache, so `cargo test` works on a fresh checkout.

## Parity is checked by the machine

Behavioral parity is not reviewed by hand — it is asserted by tests:

- **Differential tests against recorded fixtures.** The same read queries (FTS5 search, catalog, entity and fact tools) run against the same database copy and must match the recorded fixtures — the same query, the same rows (except the ANN fields, which the recall gates below cover).
- **ANN gates.** Vector search is checked with recall@k against a brute-force ground truth on the same embedding model, plus p50/p95 latency gates. The laptop budget (16 GB RAM, disk-backed index) is enforced by numbers, not by review.

A parity failure blocks a merge exactly like any other test failure: fix the code, or re-record the fixture as an explicit decision — never loosen the assertion.

## Where the tests live

Tests are co-located in each crate (`#[cfg(test)]` modules and integration tests). A test module may opt out of the `unwrap_used`/`expect_used` lints with `#![allow(clippy::unwrap_used)]` — assertions in tests make the failure explicit (see [Coding Standards](./coding-standards)).

| Crate | What is tested |
|---|---|
| `db` | DAO CRUD, pagination with filters, batch operations, transactions, FTS5 search against the knowledge DB fixture, PRAGMA parity |
| `search` | the two legs (FTS5 BM25, vector), RRF fusion, reranking, and the hybrid end-to-end path |
| `vectors` | the usearch engine, WAL + segments, compaction, and the recall/latency gates |
| `ingestion` | parsers, chunkers, NER pipelines, the `queue_tasks` event queue state machine |
| `graph` | traversal, CEL linkers, cross-domain linking with the decision cache |
| `mcp` | one test module per tool handler: success, parameter validation, edge cases |
| `cli` | subcommand dispatch and config path resolution |

## Coverage

Coverage is measured with `cargo-llvm-cov` (a cargo-installed, dev-only tool — it is not a workspace dependency):

```bash
cargo llvm-cov --workspace --html   # HTML report in target/llvm-cov/html/
cargo llvm-cov --workspace --text   # per-file table
```

The policy is **measure-first, no gates**: per-crate targets are documented ranges, not CI checks — no `--fail-under-*` flag is used locally or in CI. The per-crate target table and the current baseline numbers live in `COVERAGE.md` in the repository root.
