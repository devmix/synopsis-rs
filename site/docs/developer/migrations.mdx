# Database Migrations

There is no migration binary and no manual step: the schema is created by SQL migrations embedded into the binary and applied automatically at startup. The rules below are strict — read them before touching anything under `migrations/`.

## The layout

Migrations live at the **repository root**, not in a crate, in one directory per database:

```
migrations/
├── knowledge/          # per-dataset knowledge DB
│   └── 1-init/up.sql   # the squashed init migration
└── cache/              # global cache DB
    └── 1-init/up.sql
```

`crates/db` embeds both trees at compile time with `include_dir!` (`crates/db/src/connection.rs`) and applies them with `rusqlite_migration` 2.x (the `from-directory` feature). The SQL ships inside the binary — there is no migration directory to ship or locate at runtime.

## One squashed init migration

Each database has exactly **one** migration: `1-init/up.sql`, the squashed init. For the knowledge DB it creates the full schema in a single file — all tables (`documents`, `chunks`, `entities`, `facts`, the link tables, and the `usearch_vectors_log` ANN write-ahead log), all indexes, the FTS5 `chunks_fts` table with its sync triggers, and the `queue_tasks` event queue (folded into the init at squash time — there is no separate forward migration for it). The cache DB's init creates its own tables (the LLM/NER caches and the `app_kv` markers) in its own `1-init/up.sql`.

## `PRAGMA user_version` is the sole source of schema state

- `PRAGMA user_version` records the applied schema version — it is **1** after the init migration, and it is the **sole** source of truth about the schema state.
- The `_schema_migrations` tracking table is **deliberately not created** — there is no table of applied versions to drift out of sync with the PRAGMA.
- On open, the `db` crate reads `PRAGMA user_version`: `0` (a new file) → run the init migration; `1` → already initialized, apply nothing further, preserve the data.

## Forward-only

- Migrations are numbered directories: `<id>-<slug>/up.sql` (the current init is `1-init`).
- **No `down.sql`** — there are no rollbacks; a migration is applied once and never undone.
- **Shipped migrations are never edited.** A schema change is a **new** numbered directory continuing the sequence (for example `2-<slug>/up.sql`), applied on top of existing databases at the next startup.
- Migrations are idempotent where practical (`IF NOT EXISTS`); a subsequent startup is a no-op.

## Existing knowledge.db files are never opened

The Rust binary always builds its database **from scratch**. A pre-existing `knowledge.db` (for example, from an older version of the project) is **not opened and not upgraded** — there is no data-migration path in either direction. Vectors are handled the same way: they are rebuilt from chunk text into the usearch index and never read from any previous store — see [Vector Rebuild](../concepts/vector-rebuild).

## Testing a migration

The init migration runs on every fresh database — the `db` crate's test helper builds a database from scratch in tests and asserts `PRAGMA user_version = 1` plus the full schema. For a new numbered migration:

1. Add `migrations/knowledge/<id>-<slug>/up.sql` (and/or the `cache/` side) with the next number.
2. Keep it forward-only and SQLite-compatible; new columns need defaults or `NULL`, and unique indexes on existing data need dedup first.
3. Run `cargo test -p db` — fresh-database initialization must still pass, with `PRAGMA user_version` ending at the new value.
4. Apply it to a copy of a real dataset DB and confirm it lands cleanly on top of existing data, not just on a fresh schema.
