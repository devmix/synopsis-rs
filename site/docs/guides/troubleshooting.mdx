# Troubleshooting

A field guide to the failures you are most likely to meet, in order of how often they bite. Symptom first, then cause, then fix.

## Config not found

**Symptom** — any subcommand exits immediately with a load error naming a config path:

```
Error: ... workspace/configs/config.default.yaml ...
```

**Cause** — the binary resolves the preset in a fixed order: `--config PATH` (used verbatim, auto-search skipped); otherwise `config.{preset}.yaml` (preset defaults to `default`) is searched in this order:

1. `<exeDir>/workspace/configs/`
2. `<exeDir>/`
3. `<parent(exeDir)>/`
4. `<parent(exeDir)>/workspace/configs/`
5. `<CWD>/workspace/configs/`
6. `<CWD>/`

If none exist, it falls back to the relative `workspace/configs/config.{preset}.yaml` and fails with a load error naming that path. A moved binary, a renamed preset, or running from an unexpected directory all land here.

**Fix**:

- Pass the file explicitly: `synopsis --config workspace/configs/config.default.yaml serve`.
- Or place the preset where the search expects it — the release archives bundle `workspace/configs/` next to the binary, so `<exeDir>/workspace/configs/config.default.yaml` is the usual hit.
- `--preset NAME` selects `config.{NAME}.yaml`; make sure that exact file exists.

The full resolution order and every key it loads is in [Configuration](./configuration).

## Missing or invalid domain configs

**Symptom** — `serve` exits before doing any work, with an error about an ontology file.

**Cause** — ingestion sources and the entity/relation vocabulary live in the dataset's XML ontology at `workspace/datasets/<name>/ontology/`: `global.xml` (the global pool) plus one file per domain under `domains/`. A **missing or malformed domain XML is a startup error**, as is an invalid regex in an extraction rule (patterns are compiled at load time, and the error names the file and the rule). A missing `global.xml` is *not* an error — the global pool is simply empty.

**Fix**:

- Check that `ontology/` exists for the active dataset (the `--dataset` override wins over `dataset.name` in the config) and that `domains/` is not empty when you expect domains.
- Validate the XML — the error message names the offending file.
- The file formats and the two-layer resolution (domain first, then the global pool) are documented on the [Domains](../concepts/domains) page.

## Embedding dimension mismatch

**Symptom** — `serve` fails at startup with a dimension mismatch error: the stored vector index was created at one dimensionality, but the configured embedding model declares another.

**Cause** — you switched models without touching the dataset: the dimension no longer comes from the main config, it is the `onnx.yaml` registry entry's `vector_dim` for the selected model, and it now differs from the stored index. The [usearch index](../concepts/vector-rebuild) is created for a fixed dimension and is never silently converted.

**Fix** — two options, same recovery shape:

1. **Auto-rebuild in place** — re-run with the flag (or set `embeddings.auto_rebuild_vectors: true` in the config):

   ```bash
   synopsis serve --auto-rebuild-vectors
   ```

       **Clear-then-queue** runs: the dataset DB is cleared in place, the startup reconcile re-enqueues **all** files into `queue_tasks`, and the background worker re-embeds them through the normal pipeline. There is no direct ingestion and no vector migration — the vectors are rebuilt from the chunk text.

2. **Manual full re-ingest** — clear the dataset and restart:

   ```bash
   synopsis db clear      # confirm; removes state/ (knowledge.db + vectors/)
   synopsis serve         # startup reconcile re-enqueues everything
   ```

There is no dimension to update in the config — the dimension follows the selected model's registry entry, so the rebuild above is the whole fix. The full recovery model is on the [Vector Rebuild](../concepts/vector-rebuild) page.

## Semantic search returns nothing after an unclean shutdown

**Symptom** — after a `SIGKILL`, crash, or power loss, `search` returns lexical (FTS5) results but no semantic (vector) results for the most recent documents.

**Cause** — the vector RAM layer is persisted on a schedule (after each ingestion cycle and on graceful shutdown); a `SIGKILL` bypasses the shutdown save, so the in-progress cycle's vectors can be lost.

**Fix** — none required: the next `serve` startup runs the self-heal, which detects the missing vectors and re-embeds the affected chunks (the `ReEmbed` op) before the index serves traffic; restart and the semantic leg recovers. If it ever does not recover (e.g. the chunk rows themselves were lost), the fallback is `synopsis db clear` plus a `serve` restart. The full model is on the [Vector Rebuild](../concepts/vector-rebuild) page.

## Stuck queue tasks

**Symptom** — documents never appear in search, or re-ingestion stalls; the worker keeps failing the same files.

**Cause** — ingestion is driven by the `queue_tasks` event queue. A task that fails its maximum attempts (`ingestion.max_retries`, default 3) lands in `error` status with `last_error` populated and stops being retried until you intervene.

**Fix** — inspect and repair:

```bash
# All tasks, or filtered by source path prefix / status
synopsis queue status [--source PATH] [--status NAME]

# Re-queue failed tasks: error -> pending, attempts -> 0
synopsis queue reset-retries [--source PATH] [--identity VALUE]
```

`queue status` prints a table with columns `TYPE`, `IDENTITY`, `STATUS`, `ATTEMPTS`, `LAST_ERROR`, `NEXT_ATTEMPT_AT` (statuses: `pending`, `processing`, `done`, `error`). `reset-retries` moves the selected `error` tasks back to `pending` with a zeroed attempt counter — the background worker re-processes them on its next cycle (`auto_update.retry_failed.poll_interval_seconds`, default 60 s). If the same tasks fail again, the problem is upstream of the queue — a source, a parser, or the LLM endpoint (check `last_error` and the logs at `logging.level: debug`).

The full state machine is on the [Job Queue](../concepts/job-queue) page.

## Missing model / ONNX runtime

**Symptom** — first `serve` (or any embedding run) exits with a download or ONNX error.

**Cause** — in `embeddings.mode: local` the embedding model and the ONNX Runtime library are downloaded on first use and need network access. `load-test` is stricter: it never downloads mid-run and fails with a clear error naming the missing model.

**Fix** — verify outgoing network, then pre-fetch explicitly so the failure is visible and retryable:

```bash
synopsis onnx-runtime install
synopsis model download bge-small-en-v1.5   # or the model your preset uses
```

A download that fails **size or SHA-256 verification** means a corrupted or truncated transfer — the file is not marked installed; re-run the same command (partial files do not remain as installed). Download failures retry automatically (default 3 attempts with a delay) before erroring. See [Model Management](./model-management) for the full `model` and `onnx-runtime` reference.

## Cache DB issues

**Symptom** — `serve` logs a warning about the cache database, or LLM NER / entity linking is slower than expected (repeated network calls).

**Cause** — the global cache DB at `workspace/db/cache/cache.db` holds the persistent LLM NER responses and cross-domain linker decisions. It is an **optimization, not a dependency**: a corrupted entry degrades to a miss, and if the database cannot be opened at all, `serve` logs a warning and **continues without caching** — ingestion and search work normally, the only cost is that repeated LLM calls are paid for twice.

**Fix**:

- If the cache is unreadable or you simply want a clean slate, delete it: `rm workspace/db/cache/cache.db*` (main file + WAL/SHM side files). It is recreated on the next start; only the cached LLM decisions are lost — no knowledge data lives there.
- If LLM calls fail *through* the cache, the problem is the endpoint itself: check `ingestion.ner.llm.api_base_url` / `linker.llm.api_base_url` and the model name.

What the cache holds and why it is global is on the [Cache Database](../concepts/cache-db) page.

## Facts not appearing in search

**Symptom** — `search` results carry no related facts, or `get_entity_dossier` shows fewer facts than the documents actually contain.

**Cause** — only facts with status **`approved`** are ever exposed: search expansion, dossiers, and graph loading all query `facts` with `status = 'approved'`. The status column accepts `draft`, `pending`, `approved`, `rejected` (a CHECK constraint rejects anything else). Facts created by the pipeline are inserted as `approved` automatically, so invisible facts usually come from manual edits or a partially failed run.

**Fix** — check the queue first (a failed re-ingest leaves half-written facts):

```bash
synopsis queue status --status error
synopsis queue reset-retries
```

If the queue is clean, inspect the statuses directly:

```bash
sqlite3 workspace/datasets/<name>/state/knowledge.db \
  "SELECT id, predicate, status FROM facts WHERE status != 'approved' LIMIT 20;"
```

Approve the ones that should be public (set `status` to `approved`), or re-ingest via `db clear` + `serve` restart.

> **Note:** the fact review workflow (tooling to review `pending` facts) is **not implemented** yet. Today, fact status is managed directly in the database.

## Search returns no results or a domain warning

**Symptom** — an empty `results` list, or a `warning: unknown domain "…"; results may be incomplete` in the `search` response.

**Cause / fix**:

- **Unknown domain** — the `domain` argument must match a domain declared in the dataset's ontology and stamped onto ingested documents. An unknown domain **warns but does not fail** — results are still returned, scoped to nothing. Check the `<sources>`/`<domains>` declarations in `global.xml` and that the documents were actually ingested (`synopsis queue status`).
- **No matching content** — the documents may not be ingested yet (check `synopsis queue status` for stuck `error` jobs), or the query terminology is too specific for both retrievers; try broader terms, or drop the `domain` filter first to confirm the corpus is searchable.
- **One retriever is down** — results still come back from the other leg, but check `search.enable_lexical` / `search.enable_semantic` if one side is unexpectedly always empty (if **both** are disabled, both are force-enabled).

## Knowledge DB and vector index problems

**Symptom** — search behaves inconsistently after an experiment, a model switch, or an interrupted run; counts look wrong.

**Cause** — each dataset has two stores that must always agree: the SQLite knowledge DB (`workspace/datasets/<name>/state/knowledge.db`) and the usearch vector index (`state/vectors/`). Hand edits, interrupted runs, or a dimension change can leave them out of sync in a way no incremental update will heal.

**Fix** — inspect, then treat a full rebuild as the standard remedy:

```bash
synopsis db stats   # read-only counts: documents, chunks, entities, entity links, facts, queue jobs
synopsis db clear   # prints the same stats, asks for confirmation, then removes state/ entirely
synopsis serve      # startup reconcile re-enqueues all files; the worker re-embeds everything
```

`db clear` removes the whole dataset state directory (knowledge DB + vector index) in one call — the next `serve` rebuilds both from the sources. Note that the Rust binary **always builds its own DB from scratch** (a squashed init migration plus numbered forward-only migrations, `PRAGMA user_version` as the sole schema state); pre-existing `knowledge.db` files are never opened or upgraded — if you "see old data", you are looking at a different dataset or a leftover file outside `state/`.

## `workspace/` layout issues

**Symptom** — the binary reports a dataset with no data, or state files appear in unexpected places.

**Cause / fix**:

- **Empty `dataset.name`** — an empty dataset name means **no dataset**: the server runs with no ontology, no ingestion, no data. Set `dataset.name` in the preset (or pass `--dataset NAME`) to activate one.
- **Wrong workspace root** — everything (models, ONNX runtime, cache DB, per-dataset state) resolves under `paths.workspace_dir` (default `workspace`, relative to the CWD). A different CWD or a moved tree puts state where you do not expect it.
- **Per-dataset state** — each dataset's knowledge DB and vector index live under `workspace/datasets/<name>/state/`; the ontology and content under `workspace/datasets/<name>/{ontology,content}/`. The tree, and what is tracked vs. downloaded, is documented on the [Workspace Layout](../concepts/workspace-layout) page.

## Logging

The server logs via `tracing` in the `cli` crate only — the library crates stay logger-less. Three tolerant keys control it (unknown values are kept rather than rejected, so a typo cannot break startup):

| Key | Values | Default |
| --- | --- | --- |
| `logging.level` | `trace` / `debug` / `info` / `warn` / `error` | `info` |
| `logging.format` | `console` / `json` | `console` |
| `logging.output` | `stderr` / `stdout` | `stderr` |

Run with `logging.level: debug` for the full pipeline trace (per-stage progress, parse errors, watcher events, queue activity). JSON formatting (`logging.format: json`) is the right choice when you want to pipe the server's stderr into a log collector.

## Still stuck?

Gather these and you can diagnose most anything:

```bash
synopsis --version
synopsis db stats
synopsis queue status
curl http://localhost:8080/health   # server up? (status, version, KB counters)
synopsis onnx-runtime status
synopsis model list
```

Then re-run with `logging.level: debug` and the effective config (`synopsis --config <path> ...`) to reproduce.
