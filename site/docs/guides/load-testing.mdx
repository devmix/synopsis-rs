# Load Testing

The `load-test` subcommand serves two purposes the regular `serve` workflow cannot:

1. **Direct database population** — deterministic synthetic data is written straight into the knowledge DB and the vector index, bypassing the ingestion pipeline (no file scanning, no parsers, no NER, no LLM calls).
2. **MCP tool benchmarking** — the performance of every MCP tool is measured by invoking the handler functions directly, without HTTP: 12 benchmark cases, one per tool.

Use it for performance investigation and regression checking: how fast is semantic KNN at a given scale? What do point lookups cost? How long does the knowledge graph load take?

:::warning[Before you run]

`load-test` **clears and rewrites the dataset**: every knowledge table is wiped and repopulated with synthetic data, and the vector index is rebuilt with fresh embeddings. Point `--config`/`--dataset` at a **scratch dataset** — never a real one:

```bash
synopsis --dataset loadtest load-test --scale small
```

The run targets the dataset resolved from the config (`dataset.name` or the `--dataset` override); its `state/` directory (knowledge DB + vector index) is the one that gets cleared.

The local embedding model **must already be downloaded** — `load-test` never pulls a model mid-run. Download it first, otherwise the command fails with a clear error:

```bash
synopsis model download bge-small-en-v1.5
```

:::

## Syntax

```
synopsis load-test [--scale small|medium|large] [--seed N] [--iterations N] [--json PATH] [--no-fill]
```

Global flags (`--config`, `--preset`, `--dataset`) precede the subcommand. Flag details: [CLI Reference — load-test](../reference/cli#load-test).

| Flag | Default | Description |
| --- | --- | --- |
| `--scale` | `small` | Dataset scale: `small`, `medium`, or `large` |
| `--seed` | `42` | PRNG seed for deterministic data generation |
| `--iterations` | `100` | Measured iterations per tool case |
| `--json` | — | Write the report as JSON to this path |
| `--no-fill` | — (off) | Benchmark an existing database without generating data |

## Dataset scales

| Scale | Documents | Chunks | Entities | Facts |
|---|---|---|---|---|
| `small` (default) | 500 | 10,000 | 2,000 | 5,000 |
| `medium` | 5,000 | 100,000 | 20,000 | 10,000 |
| `large` | 10,000 | 200,000 | 40,000 | 20,000 |

The generated data spans five domains (`hr`, `product`, `engineering`, `finance`, `security`) with realistic chunk text, per-domain entity types, subject–predicate–object facts with provenance, and cross-domain entity links. All randomness flows through a single seeded PRNG (`--seed`), so two runs with the same seed produce the same data.

## How a run works

A run has four phases.

### Phase 1 — fill (skipped with `--no-fill`)

The generated dataset is written directly into the database:

1. The FTS5 sync triggers are **suspended** for the duration of the fill — bulk DML must not maintain the full-text index row by row.
2. All knowledge tables are cleared (children first) and repopulated in a single transaction.
3. The FTS5 index is rebuilt from `chunks` in one step, and the sync triggers are restored.
4. The existing vectors are deleted and the chunks are re-embedded with the configured provider — batch by batch (batch size from `ingestion.batch_size`, default 100) — into the usearch index.

If the stored vector index's dimension disagrees with the configured model, the index is **dropped and recreated** at the new dimension and the fill re-embeds everything. (Under `--no-fill` the stored index is the very data being benchmarked, so a mismatch is fatal instead.)

### Phase 2 — knowledge graph load

The knowledge graph is loaded from the database (the same code path `serve` uses at startup), and its load time is **measured separately** — node and edge counts are printed alongside it.

### Phase 3 — tool benchmark

Each of the 12 cases invokes the MCP handler functions directly, without HTTP: `search`, `catalog_overview`, `catalog_documents`, `catalog_entities`, `search_entities_by_type`, `search_facts`, `get_document_context`, `get_chunk_by_id`, `get_fact_by_id`, `get_entity_dossier`, `get_entity_relations`, `get_entity_links`. Every case runs `--iterations` measured units; the four cursor-paginated cases (`catalog_documents`, `catalog_entities`, `search_entities_by_type`, `search_facts`) follow `next_cursor` for up to 3 pages per unit.

### Phase 4 — report

The human-readable report goes to stdout; `--json PATH` additionally writes the same report as JSON (with the extra fields, e.g. `min_ms`, `total_ms`, `attempt_ms`, and the per-table fill breakdown).

The block above is from a `small` run (seed `42`, 100 iterations) — **all numbers are machine-dependent**; treat them as a reference point, not a baseline. The layout is stable.

Tool table columns:

| Column | Meaning |
|---|---|
| `TOOL` | benchmark case name (one per MCP tool) |
| `CALLS` | measured units (the latency statistics span all attempts) |
| `PAGES` | cursor pages fetched in total (paginated cases; `—` otherwise) |
| `ERRORS` | failed attempts; the first error per failed case is printed under the table |
| `AVG_MS`, `P50_MS`, `P95_MS`, `P99_MS`, `MAX_MS` | latency distribution (ms) of the attempts |
| `QPS` | throughput computed over **all** units — failed iterations count as cost |

## Interpreting the results

From the sample run, at `small` scale:

- **Point lookups are sub-millisecond.** The ID-based cases (`get_chunk_by_id` up to `get_document_context`) land at 0.03–0.05 ms — 19k–35k QPS. For direct retrieval they are essentially free.
- **Hybrid search is dominated by the semantic leg.** `search` (FTS5 + vector + RRF fusion + reranking) measures ~19 ms: the usearch KNN pass is the expensive half, and the lexical branch runs under it, so fusion adds negligible overhead.
- **Catalog tools sit in between:** 0.3–1 ms per multi-page unit (3 cursor pages).

The practical takeaway: at this scale, query latency is driven by vector search, not by the database layer or the MCP plumbing.

## Practical tips

- **Expect the first fill to dominate run time.** The embedding cache is [in-memory and per-process](./model-management#the-embedding-cache-in-memory), so every run starts cold: the `small` fill embeds 10,000 vectors from scratch, and `medium`/`large` fills take proportionally longer.
- **`--no-fill` benchmarks an existing database.** No data is generated or written; the runner uses a fixed set of generic queries and evenly sampled IDs. Handy for measuring your real knowledge base — but the stored vector index is then the data under test, and a dimension mismatch is fatal rather than auto-recreated.
- **Determinism comes from the seed.** The generator is a single seeded PRNG: identical seeds give identical data, which makes run-to-run and scale-to-scale comparisons meaningful.
- **Use `--json` for comparisons.** The JSON report carries every metric (including `min_ms`, `total_ms`, `attempt_ms`, and the per-table fill breakdown), which makes diffs easier than parsing the stdout table.
