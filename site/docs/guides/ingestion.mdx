# Ingestion

Ingestion is the "processing" stage of the [pipeline](../concepts/pipeline): documents are parsed, chunked, embedded, enriched with entities and facts, and indexed for hybrid search. There is no `sync` subcommand — ingestion is driven by the **`queue_tasks` event queue**: a startup reconcile and a file watcher enqueue doc events, and a background worker processes them (see [Job Queue](../concepts/job-queue)).

## Declaring sources

Sources are declared in the dataset ontology's `global.xml` (`<sources>` block, one `<source>` per directory):

```xml
<sources>
    <source path="./content/documents/hr" type="markdown">
        <domains>
            <domain>hr</domain>
        </domains>
    </source>
    <source path="./content/site/api.example.com" type="webpages">
        <domains>
            <domain>it</domain>
        </domains>
    </source>
</sources>
```

- `path` — directory to scan (recursively).
- `type` — **required** (the config loader rejects a source that omits it): `markdown`, `json`, `mediawiki`, `webpages`, or `unstructured`. Each value selects a different parser/chunker from the registry; the shipped `edtech` demo dataset uses `mediawiki`.
- `domains` — the domain(s) stamped onto every document from this source; this is what the `domain` filter in search matches against. See [Domains](../concepts/domains).
- `disabled` — a source can be switched off with the attribute.

The source type selects the parser implementation from the registry; an unknown type is an explicit error.

## Supported formats

| Format    | Files      | How it is handled                                                                                       |
| --------- | ---------- | ------------------------------------------------------------------------------------------------------- |
| Markdown  | `.md`      | Read as-is; chunked structure-aware on heading sections                                                |
| JSON      | `.json`    | Parsed objects/arrays; `ingestion.chunking.json.text_fields` selects which fields carry text            |
| Web pages | `.md`, `.html` | Pages grouped by page name per directory; `.md` is preferred, standalone `.html` is converted to Markdown (CommonMark) |

All parsers honor `.synignore` exclusions (gitignore semantics, inherited down the tree); the web page parser additionally skips the `static/` asset tree, which holds site assets (css/js/images), not content. Parse errors of individual files are collected and do not abort the run — other files in the source are still ingested.

## Chunking

Each chunk carries `chunk_text` (the pure body slice, with byte offsets into the source) and `search_text` (the body prefixed with the heading breadcrumb when present) — both search legs and the embedding model consume `search_text`. The chunk's own metadata bag (`section_title`, `heading_level`, `breadcrumb`, `image_paths`, …) is stored alongside it and later surfaces on search results.

### Markdown

Configured under `ingestion.chunking.markdown`: the document is split structure-aware at heading boundaries, with `max_chunk_size` (the fallback default is 1000; the shipped `config.default.yaml` preset overrides it to 8192) and `overlap_size` (default 100; an explicit 0 is preserved, not replaced) from the configuration. Each section chunk is annotated with its heading (`section_title`, `heading_level`) and a breadcrumb of the heading hierarchy.

### JSON

`ingestion.chunking.json` lists the object fields that contain text (`text_fields`, e.g. `title`, `description`, `details`; empty means all string fields) and how they become chunks:

- `combine_fields: true` — all matching fields are merged into a **single chunk per object**, rendered as `**field**: value` lines.
- `combine_fields: false` — **one chunk per field**, with the field name recorded in chunk metadata.

If none of the configured fields match, the chunker falls back to all string fields of the object; an object with no string content at all produces no chunk. JSON arrays produce one (or more) chunk per array item.

## Embeddings

Every chunk is embedded by the **local ONNX bge model** — the ONNX Runtime library and the model weights are downloaded and cached by the binary per `onnx.yaml`, so there is no external embedding service. Details:

- Embeddings are computed from `search_text` (breadcrumb + body), in batches of `ingestion.batch_size` (default 100), L2-normalized, and cached in memory (keyed by model + dimension + text, size-limited) so repeated re-ingests do not re-infer.
- The vector dimensionality follows the model: the shipped presets use **`bge-small-en-v1.5` (384-dim)** instead of the frozen **`bge-m3-int8` (1024-dim)** — a documented deviation for faster local testing, not a bug. See [Configuration](./configuration#embeddings).
- Vectors are written to the ANN index (usearch HNSW, disk-backed) **after** the SQLite transaction commits — the chunk rows in the database are the source of truth, and the index is rebuilt from chunk text, never migrated. See [Vector Rebuild](../concepts/vector-rebuild).

## Entity extraction (NER)

Two providers run over every chunk, in the order configured under `ingestion.ner`, and their results are merged into one composite set:

1. **`regex`** — rule-based extraction from the regex rules of the domain configs (`<extraction><regex-rules>` in the ontology). A rule's first capture group (or the full match without groups) becomes the entity name; duplicates by (name, type, domain) are removed and the matching rule's id is recorded.
2. **`llm`** — a remote OpenAI-compatible LLM endpoint (an HTTP client) extracts entities (and facts) from the text with structured output. The prompt includes the chunk's section context (breadcrumbs) when present; responses are validated (a confidence outside [0,1] is replaced with the default 0.5, descriptions truncated, uncertainty markers dropped) and cached in the cache DB (`llm_ner_cache`), so repeated extractions of identical text never hit the API.

**Low reasoning effort + exhaustiveness directive.** The shipped presets run NER at `reasoning_effort: low` — `gpt-oss` is a reasoning model, and `low` bounds the long-reasoning hang (`max_tokens: 8192` is the hard safety bound). To keep extraction complete at `low`, the NER system prompt carries a **soft exhaustiveness directive**: extract every explicitly-named entity in the chunk, including entities referenced only via a `[[wiki-link]]` or a bare name. It is a soft instruction (not a penalty), and it is present in both the workspace prompt override and the embedded default (the fallback).

There is deliberately no third "local NER model" provider: prose/statistical NER was deferred by human decision 2026-08-23 — a second local model stack for NER was rejected — so extraction here is rule-based + remote LLM only.

The composite stage tags each entity/fact with its provenance (source metadata + provider name) and applies the domain's `auto_publish_threshold` from the domain XML: entities below the threshold are dropped, and facts with a dropped subject or object are dropped cascadingly. Entities of unknown domains pass through unfiltered.

## Entities and facts

**Entity resolution (deduplication).** Extracted entity names are normalized and compared with a rune-aware **Jaro-Winkler** similarity. Names of the same type and domain scoring at or above `ingestion.resolver.similarity_threshold` (default **0.85**) are merged onto a single canonical record (the longest name), so "DevOps Team", "devops-team", and "DevOps Team " do not fragment the graph. Matching is blocked by `domain:type:bigram` — entities in different domains or types are never merged.

**Facts.** Structured subject → predicate → object triples are created with their domain and confidence; the subject and object are resolved as synthetic entities (lookup-or-create) and linked to the chunk. For each fact a **source with a quote** is stored — a window (±60 runes) around the first occurrence of the subject's or object's name in the chunk, trimmed at a line boundary with a "…" suffix when truncated. A cross-domain fact (subject and object in different domains) is dropped with a warning.

Facts carry a lifecycle (`draft`, `pending`, `approved`, `rejected`); only **`approved`** facts are exposed through the MCP tools.

## Cross-domain entity linking

When a run creates or updates entities, the pipeline enqueues an `entity:link` event; the background worker links those candidates against the rest of the dataset — by **CEL expressions** (`expression` method), normalized-name equality (`equals`), or an LLM decision (`llm`) — each link recording its method, confidence, and evidence. The run is incremental (only the entities created or updated by the run, never the document's full set) and idempotent, so re-running is always safe. See [Cross-Domain Linking](../concepts/cross-domain-linking).

## How ingestion is triggered

`serve` keeps the knowledge base current through the `queue_tasks` event queue — there is no separate ingestion daemon:

| Trigger              | What happens                                                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Startup reconcile** | When `serve` starts, the dataset is scanned and the diff — new or changed files — is enqueued. `--no-initial-sync` skips this step at boot.            |
| **File watcher**      | While the server runs, file changes enqueue diffs into the same queue (debounced by `auto_update.debounce_seconds`, default 1 s); a vanished file enqueues a delete, and the document's data is removed cascadingly. |
| **Background worker** | Polls the queue (`auto_update.retry_failed.poll_interval_seconds`, default 60 s) and dispatches each due task by type — `doc:index` runs the full pipeline (parse → chunk → embed → NER → entities/facts → write), `doc:delete` removes the document, `entity:link` links the candidates — with retries. A task that fails its maximum attempts (`ingestion.max_retries`, default 3) lands in `error` status with `last_error` populated. |

Deduplication by hash keeps re-ingests cheap: the SHA-256 of the content is compared with the stored one, so an unchanged document is skipped entirely, and a changed one is refreshed (old data deleted cascadingly, new data written in one transaction).

### Stuck tasks

Inspect the queue with:

```
synopsis queue status [--source PATH] [--status NAME]
```

(tabular output: type, identity, status, attempts, last_error, next_attempt_at; `--source PATH` narrows to a single source, `--status NAME` to a single status), and recover failed tasks with:

```
synopsis queue reset-retries [--source PATH] [--identity VALUE]
```

(error → `pending`, attempt counter reset; the worker re-processes them on its next cycle). The full state machine is on the [Job Queue](../concepts/job-queue) page.

### Full re-ingest

There is no `sync` subcommand. A full re-ingest is `synopsis db clear` (removes the dataset's `state/` — knowledge DB and vector index in one call) followed by a `serve` restart: the startup reconcile re-enqueues all files and the worker re-embeds them. If the configured embedding model's dimension no longer matches the stored index, `serve` reports the mismatch and exits with an error telling you to re-run with `--auto-rebuild-vectors`; with the flag, it clears the dataset and re-enqueues it (the clear-then-queue recovery) so the worker re-embeds everything — see [Vector Rebuild](../concepts/vector-rebuild).
