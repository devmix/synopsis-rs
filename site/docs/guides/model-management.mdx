# Model Management

Synopsis computes embeddings **locally**: an ONNX model is downloaded on demand from the `onnx.yaml` registry and loaded into the process through the ONNX Runtime shared library (an external `.so`/`.dylib`, also downloaded and cached by the binary). Both are managed with dedicated subcommands — no external model management needed.

## The `model` subcommand

### `model list`

```bash
synopsis model list
```

Prints every model in the `onnx.yaml` registry as a table: `NAME` (the registry identifier used by `download`/`delete`/`info`), `DISPLAY` (display name), `DIM` (vector dimension), and `STATUS` (installation state):

```
Available Models:
┌───────────────────────────────────────┬────────────────────────────────┬──────┬───────────────┐
│ NAME                                  │ DISPLAY                        │  DIM │ STATUS        │
├───────────────────────────────────────┼────────────────────────────────┼──────┼───────────────┤
│ bge-m3-int8                           │ BGE-M3 INT8 Quantized          │ 1024 │ installed ✓   │
├───────────────────────────────────────┼────────────────────────────────┼──────┼───────────────┤
│ bge-small-en-v1.5                     │ BGE Small English v1.5         │  384 │ installed ✓   │
├───────────────────────────────────────┼────────────────────────────────┼──────┼───────────────┤
│ paraphrase-multilingual-MiniLM-L12-v2 │ Paraphrase Multilingual MiniLM │  384 │ not installed │
└───────────────────────────────────────┴────────────────────────────────┴──────┴───────────────┘
```

### `model download [NAME]`

```bash
synopsis model download bge-small-en-v1.5
```

Downloads all of the model's files (per the registry's `files` list) into `<workspace_dir>/models/<name>/` (default `workspace/models/<name>/`) and marks the model installed. The name is optional — if omitted, the registry default (`models.default` in `onnx.yaml`; the shipped registry: `bge-small-en-v1.5`) is used:

```bash
synopsis model download
```

### `model info [NAME]`

```bash
synopsis model info bge-small-en-v1.5
```

Shows name, display name, description, version, vector dimension, source/repo, installation status, install date, and the expected files with their sizes (a `(checksum verified)` marker where the registry entry declares a checksum). Omitting the name shows the registry default.

### `model delete NAME`

```bash
synopsis model delete bge-small-en-v1.5
```

Removes the model directory from `<workspace_dir>/models/`. The name is **required**; deleting a model the config currently uses breaks the next embedding run — download its replacement first, and see the dimension-mismatch note below if the replacement has a different `vector_dim`.

### `model benchmark [NAME]`

```bash
synopsis model benchmark bge-small-en-v1.5
```

Measures embedding speed through the **production path** (the exact provider code used by ingestion and search). With no name, it benchmarks **every installed** registry model; with a name, just that model (which must be installed — an uninstalled target is an error telling you to run `synopsis model download <name>` first). The report starts with a hardware header (CPU model, logical CPUs, RAM, ONNX Runtime version) and then one `production:` line per model.

## Auto-download on first use

You rarely need to pre-download: with `embeddings.mode: local` and `embeddings.local.model_name` set, the model is **downloaded automatically on first use** (the first `serve` run that needs it). One exception: `load-test` never pulls a model mid-run — it fails with a clear error if the configured model is not installed, so download it first (see [Load Testing](./load-testing)).

## The `onnx.yaml` registry

The catalog of available models and the ONNX Runtime release lives in `onnx.yaml` (path configurable via `paths.onnx_config`, default `workspace/configs/onnx.yaml`):

```yaml
models:
  default: "bge-small-en-v1.5"
  entries:
    - name: bge-small-en-v1.5
      display_name: "BGE Small English v1.5"
      version: "1.5.0"
      vector_dim: 384
      files:
        - name: model.onnx
          url: "https://huggingface.co/BAAI/bge-small-en-v1.5/resolve/main/onnx/model.onnx"
          size_bytes: 133093490
        - name: tokenizer.json
          url: "https://huggingface.co/BAAI/bge-small-en-v1.5/resolve/main/tokenizer.json"
          size_bytes: 711396
```

- Each entry declares `name`, `display_name`, `description`, `version`, `vector_dim`, and `files[]` — each file with `name`, `url`, `size_bytes`, and an optional `checksum` (`"sha256:hex"`).
- **Every download is verified by URL + size + SHA-256**: the file is fetched from its URL (retries with a delay, SSRF protection against private/loopback addresses, progress display), then its size is checked against `size_bytes` — on a mismatch the file is not marked installed. A declared `sha256:` checksum is verified the same way.
- **`vector_dim` is what ties a model to the vector index** — the index is created at exactly that dimensionality. To host your own model, add an entry with its ONNX + tokenizer URLs (or a mirror), then select it with `embeddings.local.model_name`.

The full key-by-key reference for `onnx.yaml` (including the `runtime` section) is in [Configuration — the onnx.yaml model registry](./configuration#the-onnxyaml-model-registry).

## Switching models — dimension mismatch

If the new model's `vector_dim` differs from the dimension of the stored index, `serve` detects the mismatch at startup and refuses to continue with stale vectors. Fix it as described in [Troubleshooting — Embedding dimension mismatch](./troubleshooting#embedding-dimension-mismatch): re-run with `--auto-rebuild-vectors` (clear-then-queue: the dataset is cleared and the worker re-embeds everything) or start from a clean dataset (`db clear` + `serve` restart).

## The ONNX Runtime library

The ONNX Runtime shared library itself is an **external** artifact: the binary downloads the platform-specific release (version and archive URLs from the `runtime` section of `onnx.yaml`; the shipped registry: 1.28.0), unpacks it, and caches it under `<workspace_dir>/onnxruntime/` (default `workspace/onnxruntime/`). Subsequent runs use the cached library without downloading. Manage it explicitly:

```bash
# Check what is installed
synopsis onnx-runtime status

# Install the library (no-op if already installed)
synopsis onnx-runtime install

# Remove it (it will be re-downloaded when needed)
synopsis onnx-runtime uninstall
```

`status` reports the version, installation state, library path, and cache directory, plus the list of supported platforms. The shipped registry covers five platforms: `windows-amd64`, `linux-amd64`, `linux-arm64`, `darwin-amd64`, `darwin-arm64`.

## The embedding cache (in-memory)

Repeated embedding of identical text within a run is avoided by an **in-memory** cache: the key is the model name + dimensionality + text, the cache is size-limited (default 10,000 entries) and thread-safe, and a repeat request returns the cached vector without re-inference. It lives **per process, not in any database** — it vanishes when the process exits.

That is what the [job queue](../concepts/job-queue)'s content-hash dedup complements: unchanged documents are never re-embedded at all across runs, while the in-memory cache only saves repeats *within* a run (the same text appearing in several chunks).

The **persistent** caches are different: the LLM NER responses and the cross-domain linker decisions live in the **global cache DB** (`workspace/db/cache/cache.db`) and survive across runs and datasets — see [Cache Database](../concepts/cache-db). The cache DB never stores embeddings.

One more consequence of the local design: the embedding model is loaded **only** when a provider is created (the ingestion worker, or a `model benchmark` run). The query path — `search` and the other MCP tools — never loads the model.
